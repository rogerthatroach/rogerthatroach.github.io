Astraeus answers a deceptively simple kind of question: a finance leader asks for headcount, compensation cost, or open positions across an authorized part of the organization and expects an answer they can use. The language is flexible. The calculation and access rules cannot be.

The architecture therefore separates responsibilities rather than treating one model call as the system. Foundation-model stages interpret the request and shape the response. Conventional code resolves entitlement, reads governed data, performs the calculation, and validates the handoffs. The numerical path is repeatable for fixed inputs, data, code, and configuration; model routing and prose remain probabilistic.

This note is about that boundary: what crosses it, what evidence can test it, and where the design can still fail.

## The responsibility split

The useful question is not whether an LLM can call tools or produce a plausible financial answer. It is which responsibilities may remain probabilistic without weakening access control or moving calculation into generated prose.

That separation makes failures easier to locate. A routing error is not the same failure as a stale entitlement mapping. A correct aggregate with misleading prose is not the same failure as incorrect arithmetic. Each needs different evidence and a different fallback.

## Four bounded model stages

Astraeus uses five to eight foundation-model calls across four stages. The count varies with the query shape, but the responsibility split does not.

**1. Gate.** The first stage checks whether the request belongs to a supported domain and screens for out-of-scope or suspicious input. It returns a typed routing decision. Because this is a model decision, false accepts and false rejects remain possible; validation and a safe refusal path are part of the operating design.

**2. Metadata extraction.** Domain-scoped calls extract request metadata in parallel. They work from the user query and reviewed domain descriptions, not from direct access to operational stores. Their outputs must satisfy the domain contract before the deterministic path can use them. An invalid or incomplete payload stops or clarifies the request rather than silently broadening it.

**3. Answer shaping.** After entitlement and calculation, one or more answer calls receive structured aggregates for the authorized scope. These calls turn values into a readable response. They do not recompute the values, and their output is checked against the aggregate payload.

**4. Synthesis.** A cross-domain request may require a final model call to combine domain-specific answers. Numerical joins and reconciliation happen before this stage. Synthesis can organize and explain the result, but it can still omit context or introduce an unsupported interpretation.

The model-facing stages use approved foundation-model endpoints through an internal multi-provider model gateway. Provider choice is not the architectural control. The controls are the payload contract, the deterministic work between model stages, the validation at each handoff, and the fallback when a stage does not clear its checks.

Repeated-prompt studies in code generation illustrate that model output can vary under similar settings <CitationRef id={3} />. Astraeus therefore treats its own model-shaped stages as probabilistic and evaluates them accordingly. The narrower claim is that the calculation path is repeatable for fixed authorized inputs and a retained data/configuration state, not that the complete natural-language response is deterministic.

## Entitlement translation belongs in code

The entitlement problem starts in Enterprise Performance Management, where permissions reflect organizational domains, access groups, people, cost centres, and hierarchy position. The calculation store needs an executable filter. The figure follows the five handoffs that translate one into the other and shows the stop condition at each boundary.

Roughly 40,000 cost centres form the leaf level shared by the business-segment and geographic hierarchies. The business-segment hierarchy has 18 levels and roughly 9,000 rollups. A request may target one approved slice or cross several supported domains, but the same entitlement translation determines the rows available to the calculation.

The figure is a map of responsibilities, not evidence that authorization is correct. Four operating tests add evidence beyond the handoff checks shown above:

- **Narrower users remain narrower.** Differential tests compare users with deliberately nested scopes and verify that the resolved row sets preserve that relationship.
- **Every delivery path uses the same check.** Dashboard, conversational, and report flows are tested for alternate routes around entitlement resolution.
- **Hierarchy changes are regression-tested.** Reorganizations, new rollups, and cost-centre moves can change a result without changing application code.
- **Query construction stays bounded.** Identifiers come from reviewed configuration, values bind as parameters, and the generated filter is inspected before execution.

These checks provide evidence for the configured routes and test cases. They do not guarantee that an undiscovered integration, stale catalog, or operational mistake cannot violate the intended boundary.

## Calculation remains conventional

Once the authorized row set and typed request are available, Cython-compiled Python performs the domain calculation. The model does not decide entitlement and does not perform the final numerical aggregation in prose. With fixed inputs, data snapshot, code, and configuration, this layer can be regression-tested against expected structured results.

That does not make an answer automatically correct. A valid calculation can still operate on stale source data. A model can route a question to the wrong supported shape. A hierarchy can be versioned incorrectly. Answer shaping can overstate what an aggregate means. The benefit of the split is that those failures are separable: calculation tests do not have to prove language understanding, and model evaluation does not have to stand in for authorization tests.

## Events and snapshots answer different questions

Workforce movement is a useful counterexample to the idea that one representation is sufficient. Snapshots show the stock at two reporting points; paired movement records can explain whether a change occurred within one rollup, across two rollups, or cannot yet be reconciled from the available evidence.

This is not an argument that snapshots are defective. They remain useful for point-in-time reporting and independent reconciliation. Events are useful when the question is about joins, departures, or transfers between two selected scopes. Their advantage also depends on correctly paired, de-duplicated records and the hierarchy version in effect at the time. Missing or late events require explicit reconciliation rather than a mathematical assumption that the data must balance.

## Production evidence

I conceived, architected, and built Astraeus, then led its cross-functional productionisation with frontend and infrastructure peers. It has operated in the CFO Group since November 2025 across a dashboard, a conversational interface, and inbox-ready HTML reports.

The published production shape is deliberately specific:

- five to eight model calls across four bounded stages;
- Cython-compiled Python for the deterministic calculation path;
- entitlement resolution across roughly 40,000 cost-centre leaves, an 18-level business-segment hierarchy with roughly 9,000 rollups, and a geographic hierarchy;
- typed handoffs between routing, compute, answer, and synthesis;
- structured operational records for the configured request path; and
- interactive answers for supported, authorized query shapes that previously required analyst-led email and spreadsheet work.

Evidence comes from several layers rather than from the diagram alone: representative model evaluations, schema and payload tests, entitlement test cases, fixed-input calculation regressions, hierarchy-version checks, output comparisons, logs, monitoring, and user review. Each supports a different part of the claim.

## Known limits

The responsibility split reduces the number of things any one probabilistic component is asked to do. It does not eliminate probabilistic behavior or operational risk.

- The gate and metadata stages can misunderstand a request.
- A user can place sensitive information directly in query text.
- Authorized aggregates can still require handling controls.
- Entitlement catalogs and hierarchy mappings can become stale.
- Supported query shapes do not cover every financial question.
- Output checks can catch changed values without catching every misleading interpretation.
- Logs are useful only when coverage, retention, minimization, and access controls are maintained.
- A generated answer remains an aid to a responsible user, not a substitute for ownership of the decision.

The design should therefore be judged by a concrete question: can a reviewer trace each responsibility to the component that owns it, the evidence that tests it, and the fallback used when it fails? If the answer is yes, the architecture is governable. If responsibilities blur across the boundary, a polished response can hide which control actually broke.
