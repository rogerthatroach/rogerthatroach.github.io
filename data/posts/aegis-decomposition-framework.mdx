Finance analysts ask a question with subtle ambiguity baked in: *"how does our cost-to-income ratio compare against the peer average this quarter?"*, a sentence that can map to different reported KPI definitions across banks. The answer has to resolve to a specific KPI on a reproducible computation path, with the natural-language-to-KPI decision inspectable under audit.

The industry pattern here is straightforward: prompt an LLM with a schema definition and the user&rsquo;s question; let the model emit SQL; run it. Fast to prototype. Easy to demo. Inadequate on its own inside regulated finance: chain-of-thought is not an audit trail; LLM-emitted SQL is not a safety property; *"the model usually gets it right"* is not a confidence interval.

Aegis went the other way. Five sequential stages give interpretation, retrieval, ambiguity resolution, reviewed query construction, and formatting separate contracts. Model use is bounded to intent parsing and, when needed, candidate comparison. Templates produce SQL; parameters bind values; deterministic code formats the result. This post unpacks the four architectural decisions that separate decomposition-as-guardrail from the single-prompt pattern, with the alternatives that were seriously considered, the constraints each one answered, and the reasoning that produced the call. [Two Weeks, One Refactor](/blog/aegis-v2-velocity) tells the delivery chronology. [Aegis: A Five-Stage Text-to-SQL Pipeline with Explicit Failure Paths](/blog/text-to-sql) examines the controls and failure paths.

## The four architectural decisions

Four calls separate decomposition-as-guardrail from the single-prompt pattern. Each one mapped to an explicit options comparison before it landed.

### Decision 1 · Orchestration shape

Does the system give the LLM the natural-language question and ask for SQL? Or does it decompose the work into stages and bound the LLM&rsquo;s role?

<DecisionRationale option="Decomposed five-stage pipeline with bounded model use">
Three reasons, in order. First: **decomposition is a guardrail.** Each stage has a narrow contract, a testable interface, and clear failure modes. When the disambiguation gate fires, the SQL stage has not run yet. Before SQL generation runs, the resolved KPI and parameters must pass validation. That structure gives the system explicit stop points and makes the data flow easier to inspect; it does not remove the need for end-to-end tests and runtime monitoring.

Second: **the controls are testable per stage.** The SQL stage&rsquo;s reviewed-template and parameter-binding contract does not rely on the LLM emitting executable SQL. Schema checks belong to the template library and structural validator. Disambiguation behavior belongs to the confidence gate and its empirically chosen threshold. Local contracts make failures easier to test, trace, and audit, while their effectiveness still depends on configuration, validation coverage, and the evaluation distribution.

Third: **more catalog growth becomes data instead of code.** For an existing query shape, many KPI additions can be handled as reviewed catalog rows plus embedding updates. New query shapes still require a template and code review. The design reduces rule churn without eliminating engineering work.

The cost is the upfront template library and per-stage contract design, followed by ongoing review as schemas and supported query shapes change. This post does not claim a standalone payback period for that work.
</DecisionRationale>

### Decision 2 · KPI detection method

Once the intent is parsed, the system has the user&rsquo;s phrase for the KPI they want. The catalog contains overlapping names and related definitions. How does the system produce a useful candidate set?

      cons: [

      ],

/>

<DecisionRationale option="Sentence embeddings + cosine similarity threshold">
The catalog contains abbreviations and full names that exact keyword matching can miss. *NIM* is a common abbreviation for *Net Interest Margin*, so an embedding model can place the two names near one another even when their tokens differ. That proximity is only candidate-retrieval evidence: each bank&rsquo;s reported definition and catalog metadata still need to be checked during disambiguation.

The detection stage&rsquo;s job is *recall*, not precision. It returns a candidate shortlist, not a single answer. Precision is the next stage&rsquo;s job: the disambiguation gate decides whether one candidate is clearly supported or whether the model, and ultimately the user, needs to break the tie. Separating recall from precision keeps retrieval deterministic and bounds model use to the ambiguity decision.
</DecisionRationale>

### Decision 3 · SQL generation safety model

The pipeline now has a resolved KPI plus parameters (time window, entity, comparison shape). How does the system produce the actual SQL?

  decision="How is the SQL string produced, and what makes it safe?"
  options={[

      summary: 'A pre-authored, schema-whitelisted SQL template library covers the query shapes (peer comparison, time series, single-point lookup, ranking). Parameters bind through the DB driver as prepared-statement values; templates are never modified at runtime.',
      chosen: true,
      pros: [
        'Parameter binding keeps user-supplied values out of SQL syntax when every executable path stays inside the reviewed-template contract',
        'Schema compliance is reviewable at the template-library boundary and re-checked as templates or schemas change',
        'Templates are reviewable artefacts under regulatory inspection; LLM-generated SQL is not',

      cons: [
        'Template library has to be authored upfront; covers only pre-anticipated query shapes',

      ],

      summary: 'Build an AST from the parsed intent + resolved KPI; serialize to SQL.',
      pros: [

        'No string concatenation anywhere',
      ],
      cons: [
        'Materially the same as templates with extra steps: query shapes still have to be enumerated',
        'AST builder becomes the new template library, with worse ergonomics for review',
      ],

<DecisionRationale option="Template selection + parameterized binding">
The mental shift required is recognizing that *the template library is the intended SQL surface*, not the LLM. Parameter binding separates values from SQL syntax; allow-listed templates constrain tables and columns; version control makes that surface reviewable. The claim remains conditional on every execution path respecting that contract and on validation keeping pace with template and schema changes.

The defense-in-depth validation layer is intentionally redundant. An allow-list defines what is permitted; a deny-list catches known hazards but is not treated as complete; a structural check verifies query shape; a SELECT-only operation check rules out DDL or mutation; parameter type checking adds another boundary. No single check is sufficient. Together they narrow the executable surface and create several places to reject or investigate anomalous input before execution.
</DecisionRationale>

### Decision 4 · Disambiguation contract

Some KPI references are unambiguous. Some are not. What does the system do when it isn&rsquo;t sure?

<OptionsConsidered
  decision="When the KPI candidate set is ambiguous, does the system answer anyway, or does it ask?"
  options={[
    {
      name: 'Evaluation-backed threshold with clarification',
      summary: 'The LLM disambiguator produces a candidate selection plus a score. If the score clears an empirically chosen operating threshold, accept; otherwise return a clarification request listing the candidates with their definitions. The score is a routing signal, not a pointwise probability guarantee.',
      chosen: true,
      pros: [
        'Accepted-case error and clarification coverage can be measured separately on held-out queries',
        'The threshold exposes an explicit error-versus-coverage tradeoff for review',
        'Clarification cases reveal ambiguous catalog regions that need domain review',
        'Routing lower-scored cases to clarification can reduce accepted misselections on the evaluated distribution',
      ],
      cons: [
        'Depends on evaluation coverage and can drift as the catalog, model, or query distribution changes',
        'Clarification asks add a step in the user flow; some users find this friction',
      ],
    },
    {
      name: 'Always answer (highest-similarity wins)',
      summary: 'Pick the top embedding match. Always emit SQL. Surface alternatives in the response if requested.',
      pros: [
        'Frictionless interaction',
        'No LLM disambiguation cost',
      ],
      cons: [
        'Confidently-wrong failure mode is the *default*: top match on near-duplicates can easily be the wrong KPI',
        'CFO-grade analytics cannot tolerate silent misselection: once trust is broken, it does not return',
      ],
    },
    {
      name: 'Always clarify (return candidates; let the user pick)',
      summary: 'Whenever more than one candidate remains, return the candidate list and have the user choose.',
      pros: [
        'Moves the final KPI choice to the user when several candidates remain',
        'No LLM disambiguation cost',
      ],
      cons: [
        'Heavy interaction friction for cases where the top match dominates by a wide margin',
        'Ignores the LLM&rsquo;s genuine ability to disambiguate when the question + definitions make the answer obvious',
        'Pushes domain-knowledge load onto users who came to the system to escape it',
      ],
    },
  ]}
/>

<DecisionRationale option="Evaluation-backed threshold with clarification">
The disambiguation contract addresses the operational question: *how often are accepted selections wrong, and how often does the system abstain?* The gate reduces misselection risk rather than eliminating it. Scores below the operating threshold lead to clarification; scores above it are accepted only under a policy whose selective error and coverage have been measured on held-out queries. Those are empirical results to monitor, not pointwise guarantees.

Model readiness is evaluated rather than assumed. Over-confidence on near-duplicates can admit incorrect selections, while excessive caution can create too many clarification requests. Deployment and threshold decisions therefore depend on representative held-out evaluation, the accepted-error-versus-coverage tradeoff, and ongoing drift monitoring as models, catalogs, and query distributions change.
</DecisionRationale>

## What transfers

The *family* this architecture belongs to is the LLM-as-Router pattern. [LLM-as-Router in Practice — Four Decisions](/blog/astraeus-llm-as-router-framework) examines the cross-domain analytics variant. The general shape: bound the LLM to *intent* and *judgment under uncertainty*; deterministic code performs calculation and produces the registered query and result. Declared application contracts separate model-mediated work from data access and executable SQL. Decomposition is one guardrail among validation, access control, testing, and monitoring.

What transfers across instances of the family is the *shape*: the bounded LLM surface area, confidence gates where uncertainty triggers clarification, and a deterministic compute or generation backbone. What does *not* transfer is the specific load-bearing piece: in Astraeus it is hierarchy-aware allocation math across roughly 40,000 leaf-level cost centres; in Aegis it is the reviewed template library plus parameterized binding. Each system is built around the part that has to be most precise. The LLM is kept on the narrowest practical surface, while tests, validation, access controls, and monitoring enforce the boundaries in operation.

The hardest engineering is not the LLM integration. It is figuring out which one piece is load-bearing, and refusing to let the LLM near it.
