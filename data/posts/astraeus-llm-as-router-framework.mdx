Finance leadership asks questions that cross three domains in one sentence: *"headcount by division, crossed with open positions, crossed with tenure."* The calculation needs to be repeatable for the same authorized inputs, data snapshot, and configuration; the request must be scoped by entitlement; and the path needs to return within an interactive latency target. The equivalent workflow previously took days and produced line-of-business-level results only.

A common prototype pattern is to give the LLM broad tool access and let it iterate toward an answer: one model, function-calling into a financial data store through a ReAct-style loop. It is fast to prototype and easy to demo, but it expands the data, entitlement, and audit surface that must be governed in regulated finance.

Astraeus went the other way: five to eight foundation-model calls per query across four bounded stages, with a deterministic Cython-compiled Python layer between two declared application contracts. A permission-to-SQL entitlement cascade is applied *before* compute, not after. The declared interfaces limit the LLM stages to scoped metadata and structured aggregates; typed contracts, access controls, tests, logs, and monitoring are needed to verify that the deployed paths preserve those limits. This post unpacks the four architectural decisions, the alternatives that were considered, and the residual risks. [Why I Chose LLM-as-Router Over a Monolithic Agent](/blog/astraeus-llm-as-router) tells the delivery story. [Astraeus: Bounded LLM Roles for Financial Analytics](/blog/agentic-ai) examines the mechanism, evidence, and failure paths.

## The four architectural decisions

Four calls separate LLM-as-Router from the monolithic pattern. Each one mapped to an explicit options comparison before it landed.

<DecisionRationale option="LLM-as-Router + deterministic compute">
Three reasons, in order. First: **a narrower data boundary**. Alternatives where the LLM reads underlying employee records expand the model-context, telemetry, and logging surface. LLM-as-Router defines narrow typed inputs for the model-facing stages and keeps data access in a separate controlled path. That reduces exposure, but it is not self-proving: interface coverage, configuration, tests, access controls, and monitoring remain part of the claim.

Second: **repeatable calculation as a pre-condition for use.** Finance needs a numerical result that can be reproduced from the same authorized inputs, data snapshot, code, and configuration. The LLM can route requests into the deterministic compute path and phrase its structured outputs, but its routing and prose remain probabilistic. Validation, confidence gates, and visible failure handling are therefore required around both sides of the calculation.

Third: **entitlement is enforced before compute runs.** Because deterministic code owns the data path, the permission-to-SQL entitlement cascade runs *before* the compute step rather than being woven into an LLM prompt. Retained records can show the user, catalog lookup, access group, resolved entities, cost-centre set, and SQL predicate for the configured path. That supports review; it does not eliminate the need to test route coverage, catalog freshness, and failure modes.

The cost of this shape is that the deterministic compute layer has to be built and maintained. That cost was obviously the right trade, but it was the part that took real engineering.
</DecisionRationale>

### Decision 2 · Computation layer

Once the LLM is out of the compute path, *what* does compute? Supported cross-domain query shapes over roughly 40,000 leaf-level cost centres need employee-event-level netting semantics applied over movement events, not aggregates over snapshots. The compute layer is where the interactive latency target lives or dies.

<DecisionRationale option="Cython-compiled Python">
Two reasons. First: **match the team shape.** Python was already the language for everything else in the stack: routing logic, ORM, serialization, audit-log writes. Cython gave the compute layer C-level speed for the hot paths without forking the codebase into two languages. The reviewer pool stayed the same. The hiring pipeline stayed the same. The on-call runbook stayed the same.

Second: **profile first, then compile.** Cython's annotation mode shows which Python lines are still Python-level (with a visible interpreter cost) and which have been lowered to C. That made optimization a surgical activity: find the lines that matter, annotate with type declarations, recompile, re-measure. Only the profiled hot paths had to meet the interactive latency target; the rest could stay readable Python. Pure-Rust or pure-SQL alternatives would have forced an all-or-nothing rewrite.

The SQL-only path was genuinely considered and ruled out during implementation: event-level netting across cross-domain subset combinations produces query plans that the Postgres planner handles inconsistently at this scale. The computation is more readable as imperative Python over a well-indexed event log than as a multi-hundred-line window-function SQL query.

<DecisionRationale option="EPM passthrough, pre-compute">
The deciding property was **reuse of the source of truth**. The bank had spent years curating the EPM catalog (domain permissions, security groups, employee assignments, cost centres) under an established review and change-management process. Any entitlement model that did not reuse that catalog would fork the source of truth and introduce additional drift and control-review risk.

Pre-compute placement came from a narrower argument: *least privilege.* A query result that was post-filtered from a larger computation means the computation ran over data outside the user's resolved scope, and the review has to account for differential leakage and transient access. Pre-compute filtering narrows the calculation input to the entitled set and makes that review more direct. The control still depends on the cascade being current and applied on every relevant path.

The five-step cascade (domain → access → entities → cost centres → SQL) was the real engineering. Each step has typed inputs and outputs, tests, and a structured trace record. When the related records are retained, they support review of the resolved scope for the configured path; answering a broader exposure question also requires checking catalog freshness, alternate paths, configuration, and telemetry.

Aggregates cross back up from the deterministic layer. The LLM picks them up for the answer-shaping stages: phrasing the answer, combining cross-domain results, generating the right output format. The question is *how many* LLM calls participate, and in what shape.

<DecisionRationale option="Gate-decides hybrid (simple Answer path or cross-domain Answer + Synthesis path)">
The answer-shaping workload is bimodal. Most queries are single-domain and respond cleanly to a single Answer-stage call: a user asking "what is headcount for the Technology division this quarter" does not benefit from three parallel Answer-stage calls or a downstream Synthesis stage. A minority of queries are multi-domain and benefit significantly from scoped Answer-stage calls that keep each context small and focused: "headcount crossed with open positions, crossed with tenure" is the shape where the cross-domain path pays off.

The Gate stage already classifies intent to decide whether the query is in scope at all. Extending that classification to pick the answer-shape path is cheap: the information the Gate needs (how many domains the query touches, whether cross-domain reconciliation is needed) is already on its plate. That makes the hybrid architecturally clean rather than being bolted on.

The audit anchor is the typed validation contracts at each stage boundary. The Synthesis-stage call takes structured aggregate inputs and produces a structured response; numerical reconciliation rules (how rollups interact and which base number anchors a cross-domain join) are applied before the free-form phrasing step. Deterministic Python between stages handles dispatch, parallelization, privilege checks, and contract validation. These controls constrain the model's inputs and outputs, but they do not make generated prose deterministic or eliminate semantic errors; output validation, monitoring, and user-visible uncertainty handling remain necessary.

## The permission cascade in detail

The five-step cascade is the engineering that made this architecture shippable inside governance. Each step is implemented through typed inputs and outputs with a structured trace record. Those records support review of the resolved path when the relevant inputs, snapshots, code, configuration, and records are retained.

1. **Domain permissions.** The EPM organizes data into domains; the user identity resolves to a set of domain permissions. This is a direct lookup against the entitlement catalog.
2. **Access groups.** Domain permissions map to access groups with finer-grained scope: business line, geography, grain. The mapping is maintained in EPM and pulled via a periodic catalog sync.
3. **Entities.** Access groups map to the employee records the user is entitled to see: visible headcount, visible organizational rollups.
4. **Cost centres.** The atomic routing unit: roughly 40,000 leaves shared by an 18-level business-segment hierarchy with roughly 9,000 rollups and a geographic hierarchy. Queries resolve to the entitled subset that the calculation operates over.
5. **SQL WHERE clause.** The cost-centre set materializes into a SQL predicate that Postgres applies at query time. The declared compute path requires this predicate; tests and monitoring are responsible for detecting an alternate or misconfigured path.

The decision to reuse EPM rather than build a parallel model reduced the control surface. The bank already had review and change-management processes around the EPM catalog. Forking the permission model outside EPM would have created another model to review and synchronize, with drift risk whenever the source catalog changed.

## Why subset selection changes the compute shape

The system supports subset-selection queries over roughly 40,000 leaf-level cost centres, constrained by the caller&rsquo;s entitlements and supported query shapes. Precomputing every possible answer set is infeasible. Instead, the runtime resolves the authorized cost-centre subset, filters the employee-event log, and applies netting semantics to the selected rows. Previously the finance organization could not ask those questions interactively at all; the analyst time to produce one supported slice was measured in days of spreadsheet work.

Cython's role in this is blunt: the event-level netting math inside the hot loop runs in C. The rest of the layer (IO, entitlement resolution, serialization) stays in idiomatic Python. Profiling showed the hot loop was responsible for the majority of runtime on cross-domain queries, so that's where the Cython annotations concentrate.

The *previously impossible* framing is not marketing. Before Astraeus, finance-leadership questions of the form "how does headcount cross with open positions by division, at Q2" either got answered with a multi-day analyst turnaround or did not get answered at all. The combinatorial size of the question space made interactive slicing infeasible. LLM-as-Router plus Cython-compiled compute turns the question space into an interactive one.

## Coverage, guardrails, and boundary enforcement

Three properties the architecture has to maintain under real queries, including the ones that fail.

**What happens when the Gate fails.** The Stage 1 Gate call returns a structured intent object or a rejection. If the intent is malformed or flagged, the declared path returns a clarification or refusal and does not invoke Stage 2 or downstream data access. Because the Gate is probabilistic, false accepts and false rejects are residual risks that need test sets, monitoring, and a safe fallback.

**What happens when the Gate says out-of-scope.** The Gate call classifies whether the query is inside the Astraeus domain set. Questions about payroll processing, HR performance reviews, and benefits administration are out of scope. On an out-of-scope decision, the declared path terminates before metadata extraction, compute, and answer shaping, and the user receives a scoped reply directing them to the governed source system or its support owner. Classifier errors remain possible, so deterministic domain allow-lists and downstream validation provide additional checks.

**How the walls constrain exposure.** Wall 1 separates LLM intent work from deterministic data access through narrow function signatures and typed contracts. Wall 2 limits answer-shaping inputs to structured aggregates rather than underlying records. Reviewers can inspect the signatures, call sites, serializers, and logs, while tests and runtime validation check the allowed schemas. These controls reduce exposure but do not prove its absence: aggregates can themselves be sensitive, alternate integrations can bypass an intended interface, and misconfiguration can weaken a boundary. Access control, aggregation thresholds where needed, integration tests, telemetry review, and monitoring are part of the operating control set.

Configured model calls, compute steps, and entitlement resolutions write structured trace records. Those records support review of a request path when the related inputs and versions are retained. Exact replay also depends on retaining the source-data snapshot, entitlement state, code and prompt versions, model version, and sampling settings; generated text can still vary.

## Timeline + velocity

Astraeus went from the first design outline to production in ~5 months, with v2 cycles continuing after. The architecture stabilized early; most of the engineering time after month two went into the permission cascade, the Cython-compiled compute layer, and the employee-event-level ins/outs calculations. Stakeholder conversations (explaining, repeatedly, why LLM-as-Router was the right shape rather than the seductive monolithic pattern) ran in parallel through the first three months. [Why I Chose LLM-as-Router Over a Monolithic Agent](/blog/astraeus-llm-as-router) tells the story of that stretch.

## What's next: Astraeus v2

The next evolution extends the pattern without changing its shape. Three directions on the table:

- **Skill composition.** Cross-domain-path Answer-stage calls become named skills with declared input/output contracts. A new domain is added by registering a skill, not by forking the answer-shaping code.
- **Richer Gate.** The Stage 1 Gate gains access to a small set of deterministic classifiers (question-shape, temporal-shape, cross-domain-shape) that inform path selection more precisely.
- **Expanded scope.** Additional domains come online behind the same pattern (forecasting, variance analysis) each as a new deterministic compute module plus a new Stage 3 Answer-stage call for that domain. The envelope does not change.

The constraints that shaped v1 still hold. Each v2 capability needs evidence against the same four gates: repeatable calculation for controlled inputs, entitlement enforced outside the model, measured latency at scale, and reuse of the governed source of truth.

## What transfers

The LLM-as-Router pattern is not specific to CFO analytics. It applies anywhere:

- The calculation must be repeatable for the same authorized inputs and retained snapshot
- Model context should be minimized to explicitly approved fields
- Permission enforcement should be implemented outside the model and verified with tests, logs, and monitoring
- The cost of a wrong answer exceeds the cost of a slightly less elegant architecture

Astraeus was the first production shape this pattern took inside RBC; it now underlies other systems. PAR Assist applies the separation with a richer action vocabulary; [PAR Assist: Four Decisions Behind a Reviewable Drafting Workflow](/blog/enterprise-agentic-ai-framework) explains that variant. Aegis v2 applies a related boundary to intent classification and a constrained SQL surface.

The pattern transfers across system types because the constraints are shared. Giving an LLM broad data and tool access raises the same governance questions in many regulated-enterprise settings. LLM-as-Router is one compact response, provided its declared boundaries are verified in the deployed system.
