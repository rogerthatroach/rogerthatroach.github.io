Aegis v2 was a two-week concurrent refactor of the production v1 system, not a separate greenfield build. I was simultaneously running Astraeus development and the 2025 summer intern program. The refactor landed while v1 continued serving analysts.

This isn&rsquo;t a post about working harder. It&rsquo;s a post about what velocity actually looks like when two preconditions land at the same time: an architecture you&rsquo;ve already rehearsed, and a model that finally clears the bar.

## What v1 was, and what broke

RBC&rsquo;s CFO Group benchmarks financial KPIs against the Big 6 Canadian banks using the Supplementary Financial Packages each bank publishes with its quarterly earnings. Publicly available, but complex: every bank names and nests its KPIs differently, CET1 ratios live in different tables, similar-sounding metrics mean subtly different things.

Aegis v1 was a rules-based benchmarking engine I&rsquo;d already built and productionized. It worked. It earned the 2025 CFO One RBC Team Award. The trust that made the v2 sprint possible was the trust v1 had already earned.

The catalog exposed the limit. As the KPI catalog grew, the rules engine needed more maintenance to preserve coverage. Adding a new KPI meant a new rule; a near-duplicate KPI could also require disambiguation logic to keep v1 from confusing similar measures. The maintenance surface grew with both catalog size and ambiguity.

Natural-language input was the obvious cure. If analysts could just type the question they actually meant, the disambiguation problem moves into the model.

## Why I waited

I tried this earlier with a prior approved model generation. The architecture worked at demo scale. It didn&rsquo;t hold up under the catalog. Calibrated confidence wasn&rsquo;t reliable enough: the model was either over-confident on near-duplicates (silently picking the wrong KPI) or so cautious it refused to commit. Neither failure mode is acceptable in CFO-grade analytics, where a confidently wrong number is worse than no number.

So I shelved the text-to-SQL rewrite and kept v1 in production. The catalog kept growing; the rule surface kept growing; the gap between v1&rsquo;s coverage and analyst demand kept widening. I lived with it.

A later approved model generation closed enough of the gap in our evaluations. Its disambiguation performance made the confidence-thresholded decision function viable: accept above the threshold, request clarification below it. The architecture I&rsquo;d already designed and shelved could move forward with that fallback still in place.

That&rsquo;s the unlock that made the two-week sprint possible. Not architecture clarity in isolation. Architecture clarity *plus* a model that crossed the reliability bar.

## The five-stage pipeline

The spine of v2 is a decomposed pipeline where each stage owns one concern:

1. **Intent parsing:** approved LLM with constrained generation against a JSON schema. Returns a typed intent tuple: which KPI, which time window, which comparison shape, which output format. Validation retries on schema violation; clarification request on persistent failure.
2. **KPI detection:** deterministic embedding similarity search over the catalog. Returns a candidate set <em>K<sub>c</sub></em>.
3. **Disambiguation gate:** if the top candidate dominates by a clear margin, accept it. If candidates cluster (the near-duplicate problem), the LLM gets the candidate names + definitions (no values) and chooses, with a calibrated confidence score. If confidence drops below 1&minus;&epsilon;, the system asks the user.
4. **SQL generation:** template-based with parameter binding. Templates are pre-authored, schema-whitelisted SQL with typed placeholders. A defense-in-depth validation layer runs whitelist checks (allowed tables/columns), AST checks (SELECT-only, no DDL), parameter type checks, and a deny-list of forbidden keywords as a safety net.
5. **Result formatting:** deterministic. Output shape (table / chart / narrative / single value) was fixed in the intent tuple at Stage 1.

The formal paper states the assumptions behind the safety controls: reviewed templates, parameter binding, schema validation, allow-lists, and confidence-gated disambiguation. These controls reduce the query surface but do not prove injection impossible; template review, validator coverage, access controls, and runtime monitoring remain necessary. Each stage is independently testable and has an explicit fallback. The LLM handles structured intent and ambiguous-candidate selection within schemas and confidence thresholds; database access and numerical computation remain in code.

## What the two-week refactor actually required

The &ldquo;two weeks&rdquo; metric is real. What&rsquo;s misleading about it is the framing that implies the work happened in that window.

The work happened in the months before. What happened during the sprint was crystallization, not improvisation.

1. **The architecture was already rehearsed.** I&rsquo;d been living with v1 in production and knew its failure modes: where the rules engine needed patches, which KPI categories were most ambiguous, and what analysts asked for versus what v1 could answer. I&rsquo;d also prototyped the text-to-SQL refactor with an earlier model generation; on the evaluated catalog, it did not clear the held-out acceptance bar. That operating knowledge and the shelved prototype became inputs to the v2 module. When the sprint started, I was implementing a design I&rsquo;d already evaluated and then rechecked against a model upgrade.

2. **The pipeline was decomposable.** Five stages with clear contracts meant I could build and test each one independently. Intent parsing on day one. KPI catalog + embedding load on day two. Disambiguation harness on day three. Template library + validation layer on days four-five. Formatting + integration testing on the second week. No single stage needed to be right before the next could start. At any given moment two or three stages were in flight in parallel in my head. That kind of decomposition is an architectural property; it&rsquo;s also an execution property. It makes speed possible because it makes work parallelizable.

3. **Scope was ruthlessly bounded.** v2 did not do a lot of things. It didn&rsquo;t try to be a universal financial QA system. It didn&rsquo;t support free-form numerical reasoning. It didn&rsquo;t rewrite the visualization layer. Every temptation to expand scope during the sprint got deferred to post-launch. &ldquo;We&rsquo;ll see if they ask for it once it&rsquo;s in production&rdquo; is a harder answer to give than &ldquo;sure, I&rsquo;ll add that,&rdquo; but it&rsquo;s the answer that keeps the ship date real.

Underneath all three, there was capacity protection. Astraeus was mid-flight. The 2025 summer intern cohort had interns I was mentoring. Two weeks of Aegis v2 work was possible only because the architecture&rsquo;s clarity meant I didn&rsquo;t need to be in the room for most implementation decisions. I could move between workstreams without each one losing momentum.

## The result

- Core v2 refactor completed in 2 weeks against the production-proven v1 foundation
- Natural-language KPI benchmarking replacing manual Supplementary Financial Package lookups *and* v1&rsquo;s rigid query syntax
- Aegis v1 remained the production path while the v2 refactor was underway

## The pattern

Three ideas worth taking seriously:

1. **Velocity is downstream of clarity *and* model readiness.** The work that makes a two-week sprint possible is the research, prototyping, and operational exposure that preceded it. But also: the model has to clear the reliability bar your architecture demands. The earlier-model prototype was a real cost (weeks of design work) that paid off when a later approved generation made the same architecture viable months later. If you&rsquo;re trying to compress novel architectural work into two weeks against an unreliable model, you&rsquo;re not doing it in two weeks.

2. **A shelved prototype can preserve useful design evidence.** When the later model generation cleared our evaluation threshold, the earlier architecture gave the refactor a tested starting point. It reduced rediscovery; it did not make the later implementation or integration cost-free. Prototype before you can ship, and let measured model progress determine when the design is viable.

3. **Decomposable pipelines beat monoliths.** Not only for testability, not only for maintainability, also for speed. Clear stage contracts let you parallelize work in a way monolithic agent architectures cannot.

Aegis v2 is structurally a descendant of Astraeus&rsquo;s LLM-as-Router: LLMs used surgically, deterministic code handling everything else, with the LLM&rsquo;s role bounded by schemas and confidence thresholds. The systems look different because they&rsquo;re in different domains. Architecturally they&rsquo;re the same family.

The hardest part wasn&rsquo;t shipping fast. The hardest part was knowing what not to build, and knowing when to wait.
