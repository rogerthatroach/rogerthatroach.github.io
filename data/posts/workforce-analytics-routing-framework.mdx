The AI/LLM Workforce Analytics Platform was shaped by boundary decisions: where model flexibility helped, where it created unnecessary risk, and which responsibilities had to stay in controlled code. The question was never a binary choice between &ldquo;use an LLM&rdquo; and &ldquo;do everything deterministically.&rdquo;

The design serves financial questions that may cross compensation cost, headcount, and open positions. It has to interpret natural language, resolve the caller&rsquo;s authorized scope, calculate over that scope, and return an understandable answer. Treating those as one model task would make a convenient prototype. Treating them as four different responsibilities produced a system that could be reviewed and operated.

## Four operating constraints

1. **The calculation needed a stable owner.** For the same authorized inputs, source snapshot, code, and configuration, the numerical path should produce the same result. Model routing and prose could still vary, so they needed separate validation and review.
2. **Entitlement had to be enforced before calculation.** The model could not decide which records a caller was allowed to see. That scope had to come from the governed entitlement path and be applied to the calculation input.
3. **Supported subsets had to remain interactive.** The system could not precompute every possible combination of organizational leaves. It had to resolve the requested authorized subset at runtime and calculate only the supported shape.
4. **Natural language still mattered.** Users needed to ask questions in the language of finance rather than learn a query interface. The design therefore had to preserve model flexibility without making the model the data or calculation authority.

These constraints did not point to a universal architecture. They demanded local choices about responsibility.

## Decision 1: put the model at the edges

Bounded model-assisted stages handle intent and response shaping, with deterministic orchestration and computation between them.

A broader model could instead receive tool access and iteratively query the data store until it could answer.

That broad-agent design combined language interpretation, permission, retrieval, calculation, and explanation inside one adaptive loop. The system needed model flexibility for the first and last of those responsibilities, not for the middle three.

Keeping the model at the edges narrowed what each call could receive and return. It also let the application reject an out-of-scope request before controlled data access and validate structured handoffs before moving to the next stage.

The trade-off was more application-owned orchestration, schemas, and explicit failure states. A framework could not supply the domain boundary on its own.

A narrow interface is only a design claim until every deployed path, serializer, and configuration is checked against it. Model stages can still misclassify intent or misstate a result. Tests, monitoring, and visible failure handling remain necessary.

## Decision 2: keep financial calculation in code

Python owns the controlled calculation path, with Cython in the compute-intensive portions.

Letting the model calculate directly from retrieved records would sacrifice a stable numerical path. Precomputing a large catalogue of possible answers would avoid runtime calculation but could not cover the supported subset space.

Financial arithmetic needed to be inspectable as code and repeatable for controlled inputs. At the same time, the supported subset space was too large to turn every possible question into a precomputed result.

The chosen path resolves the requested subset at runtime and applies the approved calculation rules in code. Cython was a targeted implementation choice for the heavier calculation path; the surrounding application remained ordinary Python so it could be reviewed and operated by the team.

Domain-specific calculation code has to be maintained as source rules and data structures change. It is less immediately impressive than asking a model to reason over the records.

Deterministic code can still be wrong. Source-data defects, stale rules, incorrect joins, and configuration errors remain possible. Reproducibility narrows an investigation; it does not establish correctness by itself.

## Decision 3: resolve entitlement before compute

The caller&rsquo;s governed entitlement is translated into the data scope before calculation begins.

Two apparent shortcuts were to calculate over a broader dataset and filter the result afterward, or to ask the model to interpret permission instructions.

Post-filtering means the computation has already touched data outside the caller&rsquo;s resolved scope. Prompt-based permission makes a probabilistic component responsible for an access-control decision. Neither matched the intended boundary.

Pre-compute entitlement gives the calculation one explicit input: the authorized subset for this caller and request. The model can propose intent, but code resolves the scope from the current entitlement view and applies it to data access.

The application has to integrate with the governed entitlement source and handle its hierarchy, update cadence, and failure modes. That integration is substantial product engineering, not a prompt detail.

The control depends on current entitlement data and complete route coverage. A stale catalog, mapping defect, bypass path, or logging gap can weaken it. Its strength depends on every relevant path preserving and testing the boundary; the architecture does not make exposure impossible.

## Decision 4: vary answer shaping by question scope

Supported single-domain questions use a simpler answer path; supported cross-domain questions use bounded parallel answer work plus synthesis. Across the full path, the workforce analytics platform uses five to eight model calls over four stages, depending on the query shape.

One large answer call would flatten the distinction between query shapes; always using the cross-domain path would add its cost even when one domain was enough.

A single-domain question does not need the context and coordination required by a cross-domain one. Conversely, one large context can make the model responsible for reconciling distinctions that the application can preserve explicitly.

The hybrid path keeps simple work simple while allowing scoped cross-domain results to be combined after deterministic calculation. The synthesis stage receives structured results rather than underlying records.

Two answer shapes create more branches to test, and the initial routing decision must distinguish them well enough to be useful.

Parallel calls are bounded work, not independent authorities. Their outputs can disagree or omit context, and synthesis can introduce semantic error. Typed contracts, reconciliation rules, validation, and user-visible uncertainty constrain that behavior without making it deterministic.

## Responsibilities at a glance

- **Language interpretation:** model-assisted, because user phrasing varies.
- **Entitlement:** deterministic and pre-compute, because access is not a language judgment.
- **Calculation:** deterministic code, because the numerical path needs a stable, reviewable owner.
- **Response shaping:** model-assisted over structured results, because explanation benefits from flexible language.

The handoffs are as important as the components. Each boundary needs a declared schema, a failure response, and evidence that the deployed route actually uses it.

## Where this pattern does not transfer

LLM-as-Router is not a default for every analytics product. If a system operates on public data, has a small fixed query set, or can answer directly from a conventional interface, the additional model and orchestration surface may add cost without useful capability.

The pattern becomes more compelling when language is genuinely variable but permission and calculation need narrow ownership. Even then, the exact design should follow the local constraint. The Financial Peer Benchmarking Platform relies on a reviewed query-construction surface; the AI/LLM Drafting Platform relies on one agent with bounded drafting tools. Copying the AI/LLM Workforce Analytics Platform&rsquo;s topology into either system would obscure the responsibility each one must control.

## Residual-risk review

- Can the model-facing inputs be enumerated and tested?
- Is entitlement applied on every data-access path, using a current source?
- Can the calculation be reproduced from retained inputs, code, configuration, and source state?
- Are aggregates themselves sensitive at the returned grain?
- What happens when intent routing, validation, or synthesis fails?
- Can a reviewer distinguish a logged event from evidence that the complete path was followed?

A production boundary is credible only when responsibility, failure, and evidence remain legible after the prototype becomes a production system.
