## The problem

Project Approval Requests (PARs) are how major banks govern significant initiatives. They&rsquo;re high-stakes documents that require institutional knowledge, policy compliance, and cross-referencing templates, rules, and historical examples. The drafting workflow was manual and iterative: authors had to find the applicable template, reconcile policy conflicts, and determine which fields applied to a given project type.

This wasn&rsquo;t a search problem. It was an orchestration problem.

## The vision

The one-page plan framed the question simply: what if an AI assistant could guide a PAR author through the drafting process, step by step, with relevant context at the right moment? Not a chatbot. An agentic platform that tracks workflow state, retrieves scoped context, surfaces policy conflicts for author review, and supports the configured PAR types.

I handed the concept to the 2025 Amplify cohort I was managing as an ideation exercise to explore the problem space. The exploration considered several shapes for a PAR-drafting assistant and sharpened what mattered (process guidance, not search) and what didn&rsquo;t (free-form chat, more RAG layers stacked on top of each other). Then I built the production platform end-to-end.

## The architecture decisions

**The governance constraint that shaped everything.** PAR Assist was the first true agentic AI platform approved for production at the bank. The governance envelope for v1 was a single agent, one approved scope: no multi-agent orchestration. Every architectural decision below had to deliver agentic *behaviour* (branching dialog, parallel specialized work, multi-turn state) without crossing into multi-agent *shape*. That constraint is the spine of the system.

**Why LangGraph over CrewAI / AutoGen.** Two reasons, in that order. First: the evaluation favored LangGraph for its maturity, active maintenance, and fit with the reviewed deployment constraints. Second: the drafting session is shaped like a graph, not a pipeline: template selection, field-group retrieval, extraction, sometimes loop back to clarify open follow-ups. Retained checkpoints supplied the session-persistence primitive; durability still depends on successful commits and retention. CrewAI and AutoGen were considered but not deeply evaluated. Multi-agent primitives wouldn&rsquo;t have cleared the single-agent governance bar anyway.

**Why MCP tools as the action boundary.** Registered workflow actions are typed tool invocations: template selection, retrieval, compression, extraction, merge, coverage. Successful calls write structured audit records alongside state transitions. That makes the normal execution path inspectable, but the property is conditional on registry coverage, successful commits, retention, and controls that detect bypass paths.

**Why field-group retrieval beat flat RAG.** A PAR has many target fields across supported templates, with some concepts repeating across template types. In our evaluations, flat retrieval surfaced chunks from unrelated fields: too much relevant-looking text, not enough tied to a specific target. We organized the knowledge base around the *target* the LLM extracts toward: field groups aggregate logically related fields across templates. Stage-1 retrieval picks relevant groups for the session; stage-2 retrieves a bounded candidate set within each group; compression fits each group-scoped extraction payload to its context budget. Flat retrieval remained useful for Q&A, but field-scoped extraction needed the taxonomy.

**How we got parallel extraction inside a single-agent envelope.** The problem shape wanted specialist sub-agents per field domain. Governance said no. The relevant field groups became bounded, concurrently executable extraction calls, each carrying scoped context, target-field metadata, guardrails, and examples. Each response is validated against a structured contract. An ownership-aware merge expects one configured owner per target field and routes collisions or out-of-scope contributions for review. From the outside it looks agentic: branching dialog, parallel specialized work. From governance review, it&rsquo;s one agent calling tools.

**Why retained state and retrieval matter.** Transactional workflow state keeps registered checkpoints and tool transitions available for the drafting session, while vector-backed retrieval supplies bounded candidates for each field group. Structured trace records connect those actions for review when the corresponding records and versions are retained. The control still depends on successful writes, retention, access controls, and coverage of the registered path.

**Bounded model context.** The LLM operates at intent parsing and extraction nodes. User uploads and retrieved reference chunks can enter those calls, so this is not a zero-exposure claim. Classification, scoped retrieval, typed tools, and output filtering limit application-managed context to material approved for model processing. That boundary still depends on correct classification, registry coverage, and filter behavior, so it is tested and monitored rather than treated as a proof.

## The leadership lessons

The hardest part wasn&rsquo;t the architecture. It was three things.

**Scoping.** The early ideation generated a dozen possible features. The production version focuses on one job: guide a user through a PAR draft, step by step, with relevant context at the right moment. Saying no to features is harder than building them. I learned to ask: does this serve the guided-drafting promise, or dilute it? The answers were usually no.

**Parallel execution.** PAR Assist was one of several active workstreams. Clean separation of concerns wasn&rsquo;t just good engineering; it was a management strategy. When components have narrow interfaces, workstreams can progress with fewer coordination collisions. I learned to treat interface clarity as a capacity tool, not only a code-quality choice.

**Exploration before production.** Handing the concept to the Amplify cohort for ideation widened the option set: single-agent versus multi-agent envelopes, retrieval shape, dialog versus form. The architecture I built afterward had clearer rationale because those alternatives had already been explored. The practical lesson was to plan the handoff from ideation to production before either phase starts.

## The result

PAR Assist&rsquo;s pilot launched in April 2026; the full CFO Group launch across all geographies followed in May. The manual drafting workflow became a guided interactive session designed to retain source references where available and surface gaps for follow-up. A multi-agent successor is in pilot; further details will follow in a coordinated publication.

## What I&rsquo;d do differently

Start the formal architecture document earlier. Having a detailed technical design ready when delivery capacity freed up would likely have reduced startup delay.

Involve end users (PAR authors) earlier in the design process. Our initial understanding of the pain points proved directionally useful, but earlier user feedback would have surfaced edge cases sooner.

## A useful design heuristic

PAR Assist is not a control system. The same four questions&mdash;what is observed, what is estimated, what is chosen, and who acts&mdash;are still useful for explaining its workflow:

- **Observe.** Ingest supported source material through approved document-processing paths; a typed template tool guides PAR-type selection.
- **Estimate.** A two-stage retrieval path selects relevant field groups, then retrieves a bounded candidate set within each group for scoped extraction.
- **Choose.** Parallel group-scoped extraction feeds an ownership-aware merge; collisions and uncovered inputs route to review or follow-up.
- **Act.** The workflow renders a draft, retains available source references, and records registered workflow events in transactional storage.
