## 1. The problem is not SQL syntax

Text-to-SQL systems translate natural-language questions into executable database
queries. Reported Spider execution-accuracy results include 85.3% for DIN-SQL
<CitationRef id={1} />, 86.6% for DAIL-SQL <CitationRef id={2} />, and 82.3% for
C3 <CitationRef id={3} /> on the benchmark <CitationRef id={4} />. These are
external benchmark results, not evidence about Aegis or its behavior under
ambiguous language, catalog changes, and database controls.

Aegis answers a narrower question: how can a benchmarking system interpret a
user's KPI request without silently choosing the wrong metric, then execute only
a supported database query? A phrase such as "efficiency" may refer to several
legitimate KPIs. Even after the metric is resolved, a natural-language request
must not become unrestricted SQL.

The design therefore makes two boundaries explicit. Ambiguity is handled before
query construction, and free-form model output is kept away from the database
execution surface. Five stages turn those boundaries into separate contracts
that can fail closed, be tested independently, and expose a useful reason when
the system needs the user to clarify a request.

## 2. The five-stage contract

Each stage accepts a defined input, produces a narrower output, applies a primary
control, and has an explicit failure response. Later stages cannot repair an
incorrect decision made earlier, so the handoffs matter as much as the
components.

## 3. Stage 1: parse intent without choosing a KPI

The first stage turns the user's question into a typed record. Its fields describe
the metric phrase in the user's own words, the requested time period, the
comparison scope, and the desired output form. This is extraction, not
resolution. The stage must not silently replace "margin" with a particular margin
definition or write a database statement.

A model can produce the initial structured record, but a prompt is not the
control. Application code validates required fields, accepted values, dates, and
combinations against a schema. Invalid output receives a bounded retry. If the
record is still incomplete, or if the metric phrase is too vague to retrieve
meaningful candidates, the system asks for clarification.

The output is either a valid intent or a request for more information. A failed
parse calls neither the catalog search nor the database, preventing malformed
output from becoming an implicit guess.

## 4. Stage 2: retrieve from stored catalog embeddings

The second stage generates candidates; it does not decide which candidate is
correct. Each approved KPI catalog entry has a stored embedding derived from its
name, definition, and selected descriptive metadata. At request time, the parsed
metric phrase is embedded and compared with those stored representations. The
result is a bounded shortlist containing KPI identifiers, catalog descriptions,
and similarity signals.

Sentence-level embedding methods such as Sentence-BERT show why semantically
related phrases can be retrieved even when they do not share the same wording
<CitationRef id={5} />. That helps connect aliases such as "NIM" and "net interest
margin." It also creates the central ambiguity problem: "net interest margin,"
"adjusted net interest margin," and a jurisdiction-specific variant may all be
near neighbours while representing different business definitions.

Similarity is therefore evidence for candidate retrieval, not evidence that two
KPIs are equivalent. A candidate's rank can change when the catalog, descriptive
text, or embedding model changes. If search finds nothing that meets the
candidate-generation policy, the system returns an empty shortlist; it does not
manufacture a KPI identifier.

## 5. Stage 3: resolve, abstain, or ask

The third stage consumes the original question and the retrieved catalog
descriptions. It has three explicit routes:

1. **Zero candidates.** No metric is selected. The user is asked to restate the
   KPI or add context, and query construction is not invoked.
1. **One candidate.** The candidate can proceed only when it meets the evaluated
   acceptance criteria for this route. A shortlist of one is not automatically a
   correct interpretation. Weak retrieval evidence or an incomplete question
   still leads to clarification.
1. **Multiple candidates.** The system compares the question with the candidate
   names and definitions. Model-assisted disambiguation may select only from that
   shortlist. If the result does not meet the operating acceptance policy, the
   user receives the relevant alternatives or a focused clarification question.

The model's score is a routing signal, not a correctness probability. A high
self-reported score can accompany the wrong KPI, especially where definitions
differ by reporting basis, geography, or adjustment. A numerical threshold
cannot turn that score into a guarantee.

The acceptance policy is evaluated instead through observed selection and
abstention behavior on representative questions. Useful views include performance
at different coverage levels, errors among near-duplicate KPIs, clarification
frequency, and changes after catalog or model updates. The desired operating
point depends on the cost of a wrong selection relative to asking one more
question; it is not chosen from a benchmark score alone.

The stage outputs one catalog identifier or a clarification. It never outputs an
arbitrary metric name for Stage 4 to interpolate. That small interface is the
main ambiguity boundary: uncertainty remains visible until the system has an
accepted catalog object to pass forward.

## 6. Stage 4: construct SQL from reviewed patterns

Once a KPI is resolved, the database path uses reviewed SQL templates for the
supported request types. Examples include a point lookup, a peer comparison, or
a time-series result. The application selects a template from a registry and
supplies typed values such as the KPI identifier, reporting period, and entity
scope. A model does not author the executable statement.

Values and identifiers require different controls. User-influenced values are
bound through the database driver rather than concatenated into SQL text. OWASP
recommends prepared statements with parameterized queries because this keeps
bound values separate from SQL syntax <CitationRef id={7} />. Table names, column
names, sort keys, and other identifiers cannot be protected by value binding in
the same way, so they come from application-controlled mappings and explicit
allow-lists rather than from user strings.

Before execution, structural validation checks the registered path:

1. The statement contains one supported read operation.
1. Referenced relations and columns belong to the configured allow-list.
1. Functions, operators, grouping, and ordering match the selected query pattern.
1. Placeholders are complete and their bound values match expected types.
1. The selected template and output contract agree on the expected result shape.

A deny-list can flag suspicious terms, but it is only a secondary diagnostic.
It does not replace positive allow-lists, parameter binding, or structural
checks. If any required check fails, the application rejects and records the
attempt before the database call.

These application controls reduce the reachable query surface; they do not make
a universal safety claim. Template defects, configuration mistakes, and
unregistered execution paths remain possible failure modes. The database account
should independently use the least privilege needed for reads, with appropriate
timeouts and result limits. Route-coverage review and integration tests are
needed to confirm that deployed requests actually pass through the registered
path.

## 7. Stage 5: format a known result shape

The final stage receives typed rows from an approved query pattern and renders
the requested output form. Comparison tables, trend series, summary values, and
short templated sentences each have an explicit formatter. Given the same typed
rows and formatting request, application code produces the same representation;
there is no free-form model narrative at this stage.

Formatting does not validate the KPI decision or prove that source data is
correct. Its boundary is narrower: unexpected columns, incompatible types,
unsupported output forms, and empty results produce explicit states rather than
being turned into plausible prose. The formatter does not retry the database
with a different query to make an answer appear.

## 8. End-to-end behavior and evidence

A clear request can pass through all five contracts without clarification. An
ambiguous request stops earlier: zero candidates or unresolved alternatives
produce a question for the user, with no SQL execution.

The decomposition also defines what evidence belongs to each boundary:

1. **Intent parsing:** schema fixtures, missing-field cases, invalid combinations,
   and expected clarification behavior.
1. **Candidate retrieval:** retrieval coverage for known aliases, near-duplicate
   stress cases, empty-result behavior, and catalog-update checks.
1. **Disambiguation:** selection and abstention results on held-out questions,
   broken down by ambiguous KPI groups rather than only one aggregate score.
1. **Query construction:** template review, validator unit tests, parameter-binding
   integration tests, route-coverage checks, and negative cases that must not
   reach the database.
1. **Formatting:** exact-output tests for each supported result shape, including
   empty and malformed inputs.

Stage transition logs can support diagnosis by recording which candidate set,
route, template, and validation outcome were involved, subject to the
application's data-handling rules. Logs are evidence for investigation, not
proof that every call used the intended path. Runtime monitoring, permissions,
and periodic regression tests remain part of the operating control set.

## 9. What this design establishes

Aegis does not solve ambiguity by hiding it behind a single confidence score, and
it does not treat generated SQL as an acceptable database interface. It narrows
the problem in sequence: parse the request, retrieve possible KPIs, resolve or
clarify, construct a supported query from reviewed parts, and format a known
result.

The result is an inspectable set of boundaries with specific failure responses.
Its effectiveness still depends on the catalog, evaluation set, templates,
validator configuration, database permissions, and deployed route coverage.
That is the useful claim of the architecture: not that failure is impossible,
but that ambiguity and execution risk have defined places to be measured,
rejected, and improved.
