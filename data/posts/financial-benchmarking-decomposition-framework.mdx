A natural-language benchmarking system has two different uncertainty problems.

First, the user&rsquo;s phrase may map to several plausible financial KPIs. Second, even after the KPI is resolved, the system has to construct and execute a query without turning model output into an unrestricted database program.

Collapsing both problems into one prompt makes the demo shorter and the operating decision harder to inspect. The Financial Peer Benchmarking Platform separates them. Semantic retrieval produces candidates; an accept-or-clarify policy handles ambiguity; reviewed templates and parameter binding constrain the executable query.

## Two risks, two stop points

Metric resolution and query execution fail differently.

A wrong KPI selection can return a valid query against the wrong measure. A correct KPI selection can still feed an invalid or unsafe query path. One confidence score cannot stand in for both decisions, and a fluent final answer can conceal either failure.

The design therefore needs independent stop points:

- the intent must conform to a typed request;
- candidate retrieval must return a bounded, inspectable shortlist;
- unresolved ambiguity must return to the user; and
- executable queries must stay inside a reviewed surface.

## Decision 1: decompose the path

Five stages use separate contracts for intent, candidate retrieval, ambiguity handling, query construction, and formatting.

A direct model-to-SQL path would instead give the model the user&rsquo;s question and schema, then ask it to emit the query.

In the direct path, KPI selection and query construction happen inside one generation. A wrong metric, hallucinated identifier, or unsafe statement may become visible only after SQL exists. Decomposition places a validation or clarification boundary before each responsibility changes.

The five-stage structure does not make the system safe by itself. It lets each control be evaluated against a narrower question: did intent parse correctly, did retrieval include the right KPI, did the gate handle ambiguity, and did query construction stay inside the registered surface?

More stages create more schemas, configuration, and failure handling. The team has to maintain the interfaces rather than rely on one adaptable prompt.

Individually passing stages can still compose into a wrong outcome. End-to-end tests, database permissions, timeouts, monitoring, and review remain necessary.

## Decision 2: retrieve a shortlist, not an answer

Dense semantic retrieval over reviewed KPI names, definitions, and metadata returns a bounded candidate set.

Exact or fuzzy lexical matching would keep the machinery simple. Passing the entire catalog to a model would remove the separate retrieval step.

Financial catalogs contain abbreviations, related phrases, and near-duplicates. Lexical matching can miss equivalent wording; a full-catalog model prompt collapses retrieval and selection into one opaque decision. Semantic retrieval is useful when its job is limited to recall.

The retrieval score therefore answers only: which candidates deserve comparison? It is not a probability that the first candidate is correct. The downstream policy decides whether the evidence supports one candidate or whether the user has to clarify.

The catalog, embedding index, and retrieval configuration have to be versioned and refreshed. Domain metadata still needs human review.

The right KPI can be absent from the shortlist, and near-duplicates can cluster closely. Retrieval quality can drift as the catalog, model, or user language changes. The system must measure both candidate coverage and accepted-selection error on representative queries.

## Decision 3: make templates the executable surface

A reviewed query template is selected and user-supplied values are bound as parameters. Tables, columns, operations, and query shapes come from allow-listed configuration.

Model-generated SQL followed by inspection or sanitization would offer a broader query surface.

Generated SQL can be logged and checked after it exists, but each novel statement expands what the validators have to understand. Reviewed templates define the intended surface before a request arrives. Parameter binding keeps values separate from SQL syntax when every path respects that contract.

The capability is deliberately narrow. New query shapes require a template and review. The model cannot invent a join because a user phrased the question creatively.

The template library requires domain and database expertise. Schema changes and genuinely new query shapes still create engineering work.

Templates and allow-lists can be wrong or incomplete. Parameter binding does not constrain identifiers chosen elsewhere. Database privileges, structural validation, resource limits, and review of every execution path remain part of the control set.

## Decision 4: accept or clarify

A KPI selection is accepted only under an empirically chosen policy; lower-support or competing cases return to the user with the plausible definitions.

At either extreme, the system could always choose the top candidate for a frictionless flow or always ask whenever more than one candidate appeared.

Always answering hides uncertainty. Always asking transfers avoidable work back to the user. A selective policy makes the trade-off explicit: fewer clarification steps usually mean more accepted errors, while a stricter policy reduces coverage.

The model&rsquo;s score is a routing signal under that policy, not a pointwise correctness guarantee. Evaluation separates accepted-case error from clarification rate and tracks how both change as the catalog and query distribution evolve.

Clarification adds interaction, and threshold selection creates an operating decision that must be revisited rather than set once.

Held-out performance may not represent a new reporting cycle or a new phrasing pattern. Some high-scored selections will still be wrong. Analysts need to see the resolved KPI and retain a route to correct it.

## Responsibilities at a glance

- **Interpretation:** a model produces typed intent; malformed intent stops.
- **Retrieval:** dense semantic search returns candidates; it does not decide correctness.
- **Ambiguity:** the policy accepts or asks; uncertainty remains visible.
- **Execution:** reviewed templates and bound values construct SQL; database controls remain in force.
- **Presentation:** deterministic formatting presents the returned data; it does not repair an earlier selection error.

This division keeps the model on language and comparison work while leaving executable structure in reviewed code and configuration.

## What to test before adopting the pattern

- Does the evaluation include real abbreviations and near-duplicate definitions?
- How often is the correct KPI absent from the candidate set?
- What are accepted-selection error and clarification coverage at the chosen policy?
- Can any route construct SQL outside the reviewed templates?
- Are identifiers, values, operations, row limits, and execution time constrained independently?
- What evidence is retained when a user corrects a KPI selection?

The design earns trust only when those questions have observable answers. Decomposition makes them askable; it does not answer them automatically.
