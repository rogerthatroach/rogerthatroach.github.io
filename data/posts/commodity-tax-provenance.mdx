## 1. Calculation and inspection are different jobs

The Commodity Tax workflow produces a financial return from General Ledger journal rows. That calculation path and the surfaces used to inspect it are related, but they are not the same system responsibility.

The calculation path applies transformations in a fixed order. Each stage receives a defined input, produces a defined output, and passes that output to the next stage. Its job is to compute the return consistently under the rules and data supplied for that run.

The inspection path helps an authorized analyst examine selected intermediate results and the recorded relationships between them. Its job is to help answer questions such as: Which journal rows contributed to this value? Which category mapping was applied? At what point did the amount change? A configured Tableau view can make those questions easier to pursue, but viewing a number does not validate the source population, approve the rule that produced it, or sign off the return.

This separation is the central design point. Inspection should be built from the same retained identifiers and derivation records as calculation, while remaining an independent read and review concern. If the dashboard reconstructs its own version of the pipeline, the displayed explanation can drift away from the calculation it is meant to explain.

## 2. The five-stage calculation path

The public architecture has five fixed conceptual stages:

1. **Extract.** Select the journal rows in scope for the reporting period and carry forward the identifiers needed to locate them again.
2. **Reconcile.** Normalize and compare records across contributing sources, retaining the relationship between reconciled rows and their recorded inputs.
3. **Category Map.** Apply the configured tax-category mappings and retain which mapping and version contributed to each classified record.
4. **Aggregate.** Combine classified records into the values required by the return while retaining their recorded contributing population.
5. **Return.** Assemble the reporting output and the metadata needed to identify the run, period, and rule versions behind it.

The stages are sequential, but inspection does not have to mimic a left-to-right walkthrough. An analyst usually begins with a questioned output and moves backward. The architecture therefore needs both a forward calculation path and a backward route through the evidence that was retained.

## 3. What recorded lineage must retain

Database-lineage research distinguishes the records that contributed to an output from the operations that transformed them <CitationRef id={4} /><CitationRef id={5} />. This pipeline uses a coarser operational version of that idea: stable identifiers and derivation records connect retained stage outputs to the inputs recorded for them.

For that evidence to support an investigation, several conditions have to hold:

- **Contributing inputs are retained.** When a row affects a derived value, its identifier remains associated with that derivation.
- **Associations point to the right records.** A retained identifier is useful only if joins and mappings connect it to the input that actually contributed.
- **Rules are identifiable.** Category mappings and other material transformations carry the version needed to understand which rule was applied.
- **Identifiers remain resolvable.** Keys survive the relevant joins, filters, and intermediate datasets for the supported review period.
- **Aggregations preserve their contributing population.** A total can be investigated only when the records included in that total remain associated with it.

These are implementation conditions to test, not properties conferred by calling the data “lineage.” A dropped join key can sever a path. A many-to-many join can duplicate contributions. An overwritten mapping can make a prior classification difficult to explain. A filter can remove a record without retaining why it left the population.

The safest description is therefore **recorded lineage**. It says what the system retained without implying that unrecorded or incorrectly associated evidence can somehow be recovered later.

## 4. Investigating one questioned value

Suppose an analyst questions a value in the return. The investigation begins at that value and works backward through the recorded path:

1. Identify the aggregate and reporting period associated with the questioned value.
2. Expand the aggregate to the category-level records retained as contributors.
3. Inspect the mappings recorded for those records, including the applicable rule versions.
4. Follow the reconciled records back toward the extracted journal rows associated with them.
5. Compare the displayed evidence with the source material and the analyst's understanding of the rule.

That investigation can end in three different ways. The recorded path may explain the value. It may reveal an inconsistent mapping, join, or source record that needs correction. Or it may stop because the required evidence was not retained or cannot be resolved. The third outcome is not a weaker version of the first two; it is a distinct evidence gap that should remain visible.

## 5. Missing or inconsistent evidence

A usable investigation path has to represent failure rather than route around it. When a contributing identifier is missing, a dashboard should stop at the last supported stage instead of presenting an inferred source path. When the calculation and inspection joins disagree, the discrepancy should become a defect to reconcile rather than a cosmetic dashboard issue.

Common failure cases include:

- A source row contributes to an aggregate but its identifier is dropped during an intermediate transformation.
- A many-to-many join inflates a value while the inspection view displays only distinct records.
- A category mapping changes without retaining the version used by an earlier run.
- The dashboard applies a filter or join that differs from the calculation path.
- An analyst has access to the derived value but not to one of the recorded source datasets.
- A corrected source record exists, but the affected calculation has not yet been rerun and reviewed.

The operating response depends on the failure. A missing association may require lineage repair. A source defect may require a governed correction. A mapping issue may require rule review. An authorization limit may require a different reviewer. In every case, the evidence state should remain separate from the disposition: “unresolved” is more accurate than an explanation assembled from incomplete records.

## 6. Configured Tableau inspection views

Tableau provided configured inspection surfaces associated with relevant pipeline stages. It was familiar to the finance users involved, and it could present filtered stage outputs and drill-down paths without introducing a separate custom interface.

Those views are useful only to the extent that their joins, filters, rule labels, and authorization behavior match the retained pipeline records. They require their own semantic checks and maintenance. A dashboard can be available while its query is stale; it can display the right total while omitting a contributing row; or it can show a complete recorded path built from an incomplete source population.

The dashboards therefore support investigation, not automated approval. They provide a shared surface on which an analyst and the delivery team can examine the same questioned value and locate where their interpretations diverge.

## 7. Reconcile, correct, rerun, review

The human workflow continues after drill-down. An analyst raises a question, inspects the configured evidence, and reconciles the recorded derivation against the applicable source and rule. If the issue is a source record, mapping, or transformation defect, the correction follows the governed path for that artifact. The affected calculation is then rerun, and the resulting value and evidence are reviewed again.

This loop matters because changing a dashboard annotation does not change the calculation, and changing a source or rule does not update an already-produced return until the relevant stages run again. The review surface and the compute path must stay connected without being confused for one another.

The configured views exposed selected outputs and recorded paths, but not the full rulebook. Category mappings remained in transformation code, and changes continued through the data team's review and release controls. That boundary limited what an analyst could inspect directly and kept a dashboard annotation from becoming an ungoverned rule change.

## 8. What visibility cannot prove

Recorded lineage can make a question more focused. It can show which records and rule versions the supported path associated with a value. It can help distinguish a mapping issue from a source issue and give the team a common place to investigate.

It cannot establish that the original source population was complete, that every retained association is accurate, that a business rule was approved, that an analyst saw every relevant record, or that the resulting return should be accepted. It also cannot recover evidence that was never recorded.

The bounded lesson is practical: calculation should retain enough derivation evidence for authorized inspection, inspection should expose gaps and inconsistencies rather than conceal them, and accountable analysts should decide what those findings mean. Visibility improves the quality of the investigation only when the records beneath it deserve confidence.
