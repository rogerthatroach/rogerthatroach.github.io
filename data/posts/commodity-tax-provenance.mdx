## 1. Introduction

Process automation in regulated finance has a property that most software engineering treats as separate: every output number must be defensible against an auditor, a regulator, or a skeptical domain expert who has built years of intuition about what the numbers should look like. The standard pipeline-as-ETL pattern <CitationRef id={1} /> (extract, transform, load) can satisfy functional requirements but does not, on its own, make a result inspectable.

The gap is provenance. Functional accuracy requires the output to match approved rule application over the correct source population. A reconstructable chain from the output back to associated journal entries, together with versioned transformations and review evidence, makes that result inspectable; lineage alone does not establish that the business rules or source data were correct.

This paper describes the architecture used to automate the Commodity Tax return process at a major Canadian bank, where the engineering target was not just functional correctness but *provenance preservation across pipeline composition*. We model the pipeline as a sequence of graph rewrites <CitationRef id={2} />, each rewrite carrying a typed provenance relation. When transformations emit complete, correctly associated lineage edges, the recorded graph supports inspection from an output node back toward its source rows in the General Ledger journals. We then characterize the *transparency layer* (the parallel surface of Tableau dashboards through which stakeholders interact with the provenance chain) as a separate but composable abstraction over the same lineage model.

The architectural punchline is that *transparency is not a feature appended to compute*. It is a parallel structure derived from the same provenance relation used by the pipeline. Building both together reuses lineage plumbing, although dashboard semantics, access controls, and presentation still require separate engineering and review.

## 2. Problem Formulation

### 2.1 The Pipeline Domain

The system operates on General Ledger (GL) journal rows in scope for a tax-reporting period. Let:

- <InlineEquation html={tex("\\mathcal{J} = \\{j_1, j_2, \\ldots, j_n\\}")} /> be the set of in-scope GL journal rows for the period
- <InlineEquation html={tex("\\mathcal{B}")} /> be the set of tax-category buckets (e.g., recoverable, allocated, exempt)
- <InlineEquation html={tex("\\mathcal{R}")} /> be the space of returns, one number per bucket, plus metadata

The pipeline must implement <InlineEquation html={tex("F: \\mathcal{J} \\rightarrow \\mathcal{R}")} /> with the properties below.

### 2.2 Design Objectives

**Functional accuracy.** For each tax cycle, the produced return should match the result of applying the approved, versioned tax rules <InlineEquation html={tex("\\rho")} /> to the in-scope journal population:

<MathBlock html={tex("F(\\mathcal{J}) = \\rho(\\mathcal{J})", true)} />

That equality is an objective to test through reconciliation; the notation does not establish that <InlineEquation html={tex("\\mathcal{J}")} /> is complete or that <InlineEquation html={tex("\\rho")} /> is correct.

**Recorded lineage.** For each in-scope derived value <InlineEquation html={tex("v")} />, the system should retain a finite set of source rows connected to <InlineEquation html={tex("v")} /> through recorded, versioned transformation edges:

<MathBlock html={tex("P(v) = \\{j \\in \\mathcal{J} : j \\leadsto v \\text{ in } E^*\\}", true)} />

This defines what the lineage graph records. It does not claim that the recorded set is complete until edge emission, joins, filters, and aggregation coverage have been tested.

**Authorized inspectability.** For configured stages, an authorized reviewer should have a presentation function over the recorded graph state, user scope, and view parameters:

<MathBlock html={tex("\\pi_i: (G_i, u, p) \\rightharpoonup \\text{View}_i", true)} />

The partial arrow matters: a view may be unavailable because the stage is not surfaced, the reviewer lacks access, or the retained evidence is incomplete.

**Reproducibility.** Given fixed inputs, a versioned rule set, code, dependencies, and execution configuration, a rerun should produce an equivalent return. Byte-identical artifacts are not assumed unless serialization and environment details are also fixed.

### 3.2 Provenance-Carrying Graphs

We model each intermediate state <InlineEquation html={tex("\\mathcal{J}_k")} /> as a labelled directed graph <InlineEquation html={tex("G_k = (V_k, E_k, L_k)")} /> where:

- <InlineEquation html={tex("V_k")} /> is the set of data nodes after stage <InlineEquation html={tex("s_k")} />
- <InlineEquation html={tex("E_k \\subseteq V_k \\times V_{k-1}")} /> is the *provenance edge set*, each edge <InlineEquation html={tex("(v, u)")} /> records that <InlineEquation html={tex("v \\in V_k")} /> was derived from <InlineEquation html={tex("u \\in V_{k-1}")} />
- <InlineEquation html={tex("L_k")} /> is the labelling function carrying derivation metadata (rule applied, timestamp, version)

Each stage <InlineEquation html={tex("s_k")} /> is a graph rewrite that constructs <InlineEquation html={tex("G_k")} /> from <InlineEquation html={tex("G_{k-1}")} /> while extending the provenance edge set:

<MathBlock html={tex("s_k: G_{k-1} \\mapsto G_k \\text{ such that } E_k \\supseteq \\bigl(\\text{rewrite\\_edges}(s_k, V_{k-1})\\bigr)", true)} />

### 3.3 Composition Assumptions and Invariants

The recursive lineage notation remains useful, but it is an implementation contract rather than a proof that a deployed pipeline satisfies it. For a source row <InlineEquation html={tex("v \\in V_0")} />, define <InlineEquation html={tex("P(v) = \\{v\\}")} />. For a derived node <InlineEquation html={tex("v \\in V_k")} /> with recorded parent nodes <InlineEquation html={tex("\\{u_1, \\ldots, u_m\\} \\subseteq V_{k-1}")} />, define its recorded ancestry as:

<MathBlock html={tex("P(v) = \\bigcup_{i=1}^{m} P(u_i)", true)} />

Using that recursion for inspection depends on explicit conditions:

- **Edge completeness:** every in-scope transformation records every input row that contributes to a derived node.
- **Correct association:** each edge points to the right parent node and carries the applicable rule and version identifiers.
- **Stable identity:** node and join identifiers remain resolvable across the retained intermediate datasets.
- **Aggregation coverage:** every term included in an aggregate is represented in its recorded parent set.

These are invariants to test and monitor, not consequences of drawing the graph. Dropped joins, many-to-many duplication, filters that discard lineage, mutable rules without version identifiers, and dashboard joins that diverge from pipeline joins can all make the recorded ancestry incomplete or misleading.

### 3.4 Aggregation Lineage

For a sum whose contributing values have been completely recorded, the intended ancestry is the union of their recorded ancestry sets:

<MathBlock html={tex("P\\bigl(\\sum_{i} v_i\\bigr) = \\bigcup_i P(v_i)", true)} />

This is a bookkeeping rule for the lineage implementation, conditional on complete edges and correct aggregation semantics. It does not demonstrate that the source population, mapping rules, or resulting amount is correct. Subject to those boundaries, an analyst can expand an aggregated number toward its recorded contributing rows by traversing the graph.

## 4. The Transparency Layer as Parallel Structure

### 4.1 Dashboards as Presentations

The Tableau dashboard for stage <InlineEquation html={tex("s_i")} /> is formalized as a presentation function <InlineEquation html={tex("\\pi_i")} /> over the graph state <InlineEquation html={tex("G_i")} />:

<MathBlock html={tex("\\pi_i: G_i \\rightarrow \\text{HTMLView}_i", true)} />

The presentation function is intended to be read-only: given the same graph state, authorized user scope, and view parameters, it should return an equivalent view without modifying <InlineEquation html={tex("G_i")} />. This separates inspection from computation while leaving authorization, semantic correctness, and view-query testing as explicit responsibilities.

### 4.2 Drill-Through as Provenance-Edge Traversal

A drill-through interaction (an analyst clicking from a derived number back to the rows recorded as contributing to it) is a backward traversal of the provenance edge set. Given an aggregated value <InlineEquation html={tex("v \\in V_k")} />, define the configured traversal as:

<MathBlock html={tex("\\text{drill}(v) = \\{u \\in V_0 : (v, \\ldots, u) \\in (E_1 \\cup \\cdots \\cup E_k)^*\\}", true)} />

where <InlineEquation html={tex("(E_1 \\cup \\cdots \\cup E_k)^*")} /> is the transitive closure of the recorded provenance edges back to <InlineEquation html={tex("s_0")} />. For a final-stage value, the closure is <InlineEquation html={tex("(E_1 \\cup E_2 \\cup E_3 \\cup E_4 \\cup E_5)^*")} />.

The drill-through is consistent with the recorded graph only when its query traverses the same versioned edges and applies the intended authorization filters. It can surface the intended source rows only to the extent that edge emission, joins, and dashboard semantics are complete and correct. It cannot expose lineage that was never recorded, validate the source population or business rules, or establish that an authorized view contains every row in the underlying population.

### 4.3 Reusing Lineage Still Has Costs

A naive reading of this architecture suggests the transparency layer is free: once provenance is preserved, dashboards are just queries over the provenance graph. This is partially correct: the *information* needed for the dashboards is already in <InlineEquation html={tex("G_k")} />. What is not free is the *presentation engineering*: choosing what to show, how to summarize at each stage, and how to design the navigation between stages so that an analyst’s drill-through is fluent rather than mechanical.

The transparency layer can reuse the pipeline’s lineage plumbing, but it still carries costs for dashboard authoring, semantic validation, access control, performance, and maintenance. Building both surfaces together avoided a second lineage implementation in this case; that is an observed design advantage, not a universal cost guarantee.

## 5. Inspection and Reviewer Confidence

### 5.1 Qualitative Delivery Observation

During delivery, reviewer questions were easier to investigate when an output exposed a path through recorded transformation stages toward its contributing source rows. Drill-through gave the team a practical way to move from “this number looks wrong” to either an explanation of the recorded derivation or a focused defect investigation.

This was a qualitative workflow observation, not a measured trust function. No causal adoption threshold, fixed number of review cycles, or zero-anomaly point is claimed here. Reviewer confidence can also depend on source quality, rule governance, access controls, reconciliation evidence, operating history, and the quality of the manual comparison process.

### 5.2 Boundary of the Observation

Lineage can reduce the effort required to investigate an output, but it does not make the output correct or guarantee adoption. An incomplete lineage graph can create false confidence, while a system without embedded drill-through may still be reviewable through other evidence. The relevant design lesson is narrower: when lineage already exists, exposing it through an authorized inspection surface can make review more direct.

## 6. Implementation Notes

### 6.1 PySpark + CDP

The compute pipeline runs as a sequence of PySpark jobs on Cloudera Data Platform (CDP). Each stage emits an intermediate dataset with stable identifiers carried forward as provenance keys. CDP supplies logging and access-control capabilities <CitationRef id={3} />; whether the deployment meets a particular control requirement depends on configuration, review, and operating evidence.

### 6.2 Tableau as the Presentation Layer

Tableau was chosen over a custom inspection UI for two reasons: (a) the finance team already had Tableau muscle memory; introducing a new tool would have added adoption cost on top of automation cost, and (b) Tableau joins could implement the configured lineage traversal in a familiar drill-down interface. Correctness still depends on those joins matching the versioned pipeline relations and applying the intended authorization filters.

### 6.3 Provenance Mechanism

In the deployment, provenance is preserved through stable join keys carried forward across stages, with explicit provenance tables for the category-mapping stage where the derivation is non-trivial. The full mechanism is implementation-specific and not the focus of this paper. The lineage relationships above apply only when the mechanism records complete, correctly associated edges for every transformation in scope.

## 7. What I Would Build Differently

The first dashboard set surfaced provenance for *outputs* but not for *rules*. An analyst could drill from a derived number back to the source GL rows, but the rules that produced each category mapping lived in PySpark code, modifiable only by the data team. New tax categories or re-categorizations of existing GL accounts therefore required code changes and redeploys.

Formally, this is a missing presentation function. Let <InlineEquation html={tex("\\rho")} /> be the rule set. The dashboards include <InlineEquation html={tex("\\pi_i")} /> over data states <InlineEquation html={tex("G_i")} /> but no <InlineEquation html={tex("\\pi_\\rho")} /> over the rule set itself. A *mapping-rules dashboard* would have provided <InlineEquation html={tex("\\pi_\\rho")} />, letting analysts inspect, propose, and (with code-review approval) extend rules through the same drill-down idiom they already used for outputs.

This is the second-order application of the transparency-as-architecture principle: transparency over outputs can make review more direct; transparency over the *rules that produce the outputs* can support shared ownership.

## 8. Related Work

**Provenance in databases.** The data-provenance literature <CitationRef id={4} /><CitationRef id={5} /> formalizes why-provenance and how-provenance for SQL queries. Our pipeline operates at a coarser granularity (rows-to-rows across pipeline stages, not tuple-to-tuple within a single query) but shares the algebraic structure.

**Internal-control frameworks.** COSO’s Internal Control—Integrated Framework <CitationRef id={6} /> frames objectives and principles for effective internal control; it does not prescribe an ETL architecture. The design described here treats provenance as a first-class pipeline object that can also support a parallel transparency surface, while control effectiveness still depends on implementation and operating evidence.

**Human-in-the-loop systems.** Human-AI interaction research <CitationRef id={7} /> examines how explanations and inspection affect reliance and review. The delivery observation here is qualitative; it does not establish a causal trust model.

## 9. Conclusion

Process automation in regulated finance has a property that ordinary ETL does not address on its own: every output must be defensible to a domain expert who has built years of intuition about what the numbers should look like. Functional correctness and auditability are both necessary; neither is sufficient without valid source data, approved rules, effective controls, and human review.

The architecture above pairs a five-stage pipeline that records provenance edges with a Tableau presentation layer whose drill-throughs traverse those recorded edges. The shared lineage structure reduces duplicate data plumbing and makes the two surfaces composable, subject to lineage-completeness and dashboard-semantic checks.

The deeper claim is that *transparency is not a feature*. It is an architectural concern for systems that take auditability seriously. Surfacing derivations gives reviewers evidence they can inspect; whether that earns enough trust to replace a manual process still depends on accuracy, control effectiveness, operating history, and accountable human decisions.
