## 1. The run is the starting point

The Commodity Tax workflow ran as a large Dataiku scenario containing Python and Spark code. It processed General Ledger data through extraction, reconciliation, category mapping, aggregation, and return preparation. These five conceptual stages summarize the workflow; they do not imply that the scenario contained only five steps.

Every run saved each input and resulting intermediate file. Shared-storage folders were organized by run date and time, with corresponding partitions on the enterprise data platform. PySpark supported retrieval and navigation of the partitioned datasets; the saved files provided another access path to the run data.

This organization matters when a result is questioned. The investigation starts with the data used and produced by that run, instead of whichever dataset happens to be current.

## 2. Stage outputs remain available

The five-stage view gives reviewers a map of the calculation:

1. **Extract.** Retrieve the General Ledger data in scope for the workflow.
2. **Reconcile.** Compare and reconcile the contributing data.
3. **Category Map.** Apply the tax-category mappings.
4. **Aggregate.** Combine the mapped values into the required totals.
5. **Return.** Prepare the reporting output.

Inputs and resulting intermediate files are saved throughout the scenario. Multiple Excel reports and dynamic Tableau dashboards accompany each stage, supporting audit and debugging while the underlying stage data remains available for closer examination.

The calculation moves forward, but an investigation may move backward. An unexpected aggregate can lead to an examination of mapped records, the preceding reconciliation, and the original input from the same run.

## 3. Three ways to examine the work

**Saved datasets** preserve the inputs and intermediate results for a particular run. The folder and partition organization helps the team retrieve the stage data it needs.

**Excel reports** expose results at each stage for direct examination. They are part of the automated delivery, rather than merely a remnant of the earlier manual process.

**Dynamic Tableau dashboards** provide interactive inspection of the stage results. The dashboards therefore support investigation, not automated approval.

These surfaces complement one another. A report can identify an unexpected amount, a dashboard can help narrow the question, and the saved data can support a closer comparison of the relevant transformation's input and output.

## 4. Investigating a questioned return value

A practical investigation follows the saved work of the run:

1. Identify the run date and time associated with the questioned result.
2. Open the relevant stage report or dashboard and check that it represents the same run.
3. Retrieve the saved input and output for that stage through the file or partitioned-data path.
4. Compare the records and calculation. If the issue originated earlier, examine the preceding stage's saved output.
5. Review the source data, mapping, or implementation with the people responsible for it.

## 5. Keep the investigation aligned with the run

Run-organized storage helps separate one execution from another, but the reviewer must still select the appropriate data. Comparing outputs from different runs, or a dashboard using different filters from the report under review, can obscure the original question.

Useful checks include whether the input and intermediate files belong to the intended run, whether the report and dashboard represent that run, and whether their filters and aggregations match the comparison being made.

Saving all inputs also cannot establish that an upstream source supplied everything it should have. Data retention preserves the material received by the workflow; source completeness remains a separate review concern.

## 6. Corrections and the next run

If the investigation identifies a source, mapping, or implementation problem, the responsible team reviews the correction. The subsequent calculation and its reports then need to be checked again. Earlier saved runs remain useful comparison points.

Mapping logic remained in code, with changes passing through the data team's review and release process. Reports and dashboards supported examination of results; changing their presentation did not itself correct a transformation.

The architecture made a complex scenario easier to inspect by retaining its inputs and intermediate work and providing multiple review surfaces at each stage. It supported audit and debugging without making retention a guarantee of correct rules, complete sources, or identical replay.
