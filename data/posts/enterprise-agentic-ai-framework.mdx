The AI/LLM Drafting Platform had to guide an author through a branching, multi-turn project funding request workflow without turning every useful piece of work into another agent. Production v1 therefore uses one LangGraph graph to own the workflow and registered MCP tool routines to perform bounded work inside it.

## Four operating constraints

1. **One reviewed single-agent scope.** Production v1 could branch, use tools, and retain state, but it could not delegate control to independent sub-agents.
2. **A session spans turns.** Template choice, candidate fields, open questions, and review state have to remain coherent when a session pauses and resumes.
3. **Evidence serves known targets.** The workflow drafts a structured document, so retrieval should support fields in scope rather than return one undifferentiated set of plausible passages.
4. **The author remains accountable.** Missing coverage, conflicting candidates, and uncertain interpretation need a route back to clarification or review.

## Decision 1: put one graph in charge

A LangGraph graph owns each workflow transition. Application code uses explicit nodes and edges for intake, template confirmation, field-group work, merge, coverage review, clarification, and response. Successfully retained checkpoints allow the supported session path to continue across turns.

A hand-rolled state machine could provide the same conceptual control without an orchestration-framework dependency. It was a credible alternative because the production design needed one controller, not multi-agent coordination.

The workflow already had branching and return paths. Representing those transitions directly fit better than rebuilding routing, checkpoint integration, and tool dispatch around a linear chain. That choice reflected the reviewed workflow, not a belief that LangGraph is universally superior.

The trade-off is more setup and harder debugging than a short sequence. A checkpoint is useful only when the state schema is complete, the write succeeds, and recovery distinguishes finished work from an interrupted transition. Tests and monitoring still have to establish those properties.

## Decision 2: make registered tools the action boundary

Bounded workflow actions use registered MCP tools with declared inputs and outputs. The application pairs successfully committed actions on that registered path with structured records that support later review.

Plain application functions with custom validation and logging could implement the same business work. That alternative offers direct control, but each function needs its own wrappers and evidence checks, expanding the surface where coverage can drift.

One declared dispatch surface makes a specific question testable: did every supported action that committed produce the expected record? MCP supplies typed tool contracts; the application remains responsible for registry coverage, authorization, validation, persistence, and failure handling.

Those contracts take time to design and version. A registered interface does not prove that values are correct or that every possible action used the interface. Failed writes, bypass paths, incomplete retention, and configuration errors remain operating risks.

## Decision 3: retrieve for a field, not for the whole document

The target document is organized into groups of related fields. The workflow first identifies which groups matter for the current session, then searches the approved references associated with each selected group. Each extraction task receives the fields and evidence for one bounded scope.

A flat dense-retrieval pass over all approved chunks is simpler to build and remains useful for open-ended question answering. In the evaluated drafting workflow, however, it mixed passages that looked relevant to the subject while serving different target fields.

A project funding request has a known output shape. Using that structure before retrieval narrows the question from "what text resembles this document?" to "what evidence can support these fields?" References may still overlap across groups even though each target field has one configured owner.

The field taxonomy and its reference mappings become maintained product assets. A stale owner, missing mapping, broad group, or weak retrieval result can still supply the wrong evidence. Representative retrieval evaluation, mapping review, and visible gaps remain necessary.

## Decision 4: run bounded calls, not independent agents

Selected field groups become units of bounded work. Where capacity permits, extraction calls can run concurrently. Each receives one scoped task, returns typed candidate values, and hands control back to the graph. Ownership-aware merge code accepts configured fields and surfaces collisions or out-of-scope contributions.

One large extraction call would stay inside the single-agent boundary and simplify dispatch, at the cost of a wider context containing unrelated fields, instructions, and evidence. A sub-agent per group mapped neatly to the problem, but it did not fit the reviewed v1 scope.

Concurrency did not need to change orchestration ownership. Bounded calls preserved one controller while giving specialized work smaller inputs and independent validation boundaries.

The design adds concurrency limits, schemas, an ownership map, and merge logic. A poor group boundary can overload a call or omit a field. A configuration defect can create a collision. Coverage checks can miss a weak candidate. Detected issues therefore return to review rather than being resolved silently.

## Responsibility by design

The goal is not maximum autonomy. It is explicit responsibility: one component owns control, bounded routines perform declared work, configured checks expose known gaps, and an author decides what moves forward.

That structure does not make model output deterministic or evidence complete. It makes the remaining questions easier to ask: what state was retained, what context reached each task, which fields a routine could write, where uncertainty surfaced, and what stopped the workflow before review. Those are the properties to evaluate when applying the pattern to another structured drafting process.
