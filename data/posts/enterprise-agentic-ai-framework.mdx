Enterprise organizations run on structured processes. Project approvals, budget requests, compliance reviews: high-stakes, document-heavy workflows riddled with institutional knowledge that lives in people's heads rather than systems.

A chatbot alone does not cover that workflow. The user needs something that understands where they are in a multi-step process, holds context across the session, pulls relevant reference material at the right moment, and surfaces contradictions between policy sources so the author can resolve them.

Retrieval-augmented generation is one component of the design <CitationRef id={7} />. The system-level problem is orchestration over a structured form. This post walks through the architecture at <Glossed>PAR Assist</Glossed> inside <Glossed>RBC CFO Group</Glossed>, the first true agentic AI platform approved for production at the bank.

## Constraints before choices

Four constraints shaped every decision below. One is governance, two are regulatory/technical requirements, one is the shape of the source material. Every downstream choice was evaluated against these first; aesthetics second.

### Decision 2 · Action boundary

Every registered workflow action (pick a template, retrieve a group, extract fields, run a coverage check) passes through a typed contract and writes an audit record on successful commit. That makes the normal path inspectable; registry coverage and log-completeness checks still matter.

<DecisionRationale option="MCP tools">
The property we care about is: *every registered workflow action that commits has a corresponding audit record.* MCP gives those actions one typed registry and dispatch path, which makes the property testable. It does not prove that no bypass, failed write, or unregistered administrative path exists; those cases require access controls, integration tests, and log-completeness monitoring. Free-form function calling can also be logged, but it requires more wrappers and coverage work.

In regulated finance, the control has to be evidenced. MCP narrowed the surface that needs that evidence.

A concrete example: template selection is itself an MCP tool. It takes the user's uploaded material and their responses to decision-tree questions (project type, spend tier, business line, regulatory exposure) and returns a typed template-id with a confidence score. Successful calls retain structured inputs, outputs, and timestamps, giving reviewers evidence for how a selection was made. Completeness still depends on the logging and retention controls above.
</DecisionRationale>

### Decision 3 · Retrieval shape

PAR templates are large. Across the supported PAR types there are many fields, and some recur across templates. In our evaluations, flat chunk retrieval against policy and guideline documents produced noisy results for a drafting session: too much relevant-looking text, not enough that mapped cleanly to a target field.

The shape we needed is **field-group retrieval**: organize the knowledge base by the *target* the LLM is extracting toward, not by source document.

      cons: [

      pros: ['Would preserve inter-document references in policy documents.'],

/>

<DecisionRationale option="Two-stage retrieval with group taxonomy">
The insight is that a PAR has a known target shape. We know which fields we're trying to fill before we retrieve anything. If we organize knowledge by those fields (group related fields together across templates, attach the relevant policy/guideline/example chunks to each group) retrieval becomes a lookup into a structure the LLM already understands.

**Stage 1** picks relevant groups for the current session using uploaded-document similarity and template-selection context. **Stage 2** runs a bounded similarity search over the references associated with each group. A compression pass reduces each result set to a payload that fits alongside a scoped batch of target-field metadata in the approved extraction model's prompt.

Flat retrieval remained useful for Q&A, but our evaluations found it too noisy for structured extraction across categorically different template fields.
</DecisionRationale>

### Decision 4 · Extraction within the single-agent envelope

This is where the governance constraint (single-agent envelope) met the problem shape (parallel work across field groups). The natural answer would have been multi-agent orchestration: one sub-agent per group, each a specialist. Governance said no.

<DecisionRationale option="Parallel LLM calls, one per relevant group">
The relevant groups picked by stage-1 retrieval become the units of concurrency. A bounded number of calls can run at once, each carrying one group's compressed references, a scoped batch of target-field metadata, and the instructions and few-shot examples specific to that task. Each returns a JSON dictionary of candidate field values.

Each target field has one expected owner group, while the underlying reference subsets may overlap because the same source can inform several fields. Merge code accepts values only for the owner's configured keys. Duplicate or out-of-scope contributions are treated as collisions and surfaced for review rather than resolved by last-writer-wins.

The result is scoped extraction that can run concurrently and then pass through schema validation and ownership-aware merge code, all inside a single-agent envelope. Coordination lives in graph logic rather than in independent agent processes; each model call receives a bounded extraction task and returns structured data for validation.
</DecisionRationale>

## Transactional workflow state

The public architectural point is the separation of responsibilities: a transactional workflow store retains declared checkpoints, validated session state, and registered action records, while a vector-backed retrieval layer indexes approved reference material.

Committing a state transition with its corresponding registered action record reduces inconsistency between the workflow's declared state and its audit evidence. It does not prove complete reconstruction: successful writes, registry and schema coverage, reference-version capture, access controls, and retention still have to be tested and monitored.

That level of detail is enough to explain the control pattern without publishing deployment topology. Storage products and boundaries can change independently as long as the workflow preserves those tested properties.

## Coverage, guardrails, and few-shot examples

Three quality layers run through the system, each at a different node in the graph:

1. **Per-group instructions and validation:** each extraction prompt carries field constraints and phrasing guidance. Prompts and few-shot examples influence behavior but do not enforce it, so responses are schema-checked and violations follow a review or retry path.

2. **Per-group few-shot good/bad examples:** small, curated libraries of example values and review notes. They give the model concrete examples of acceptable and unacceptable output for a field, but validation and author review remain separate controls.

3. **Session-level coverage analyzer:** runs after the merge. Checks the full merged state against the guideline set. Produces a coverage report + a prioritized list of intelligent follow-ups. The follow-ups are what turn PAR Assist from a field extractor into a collaborator: "You haven't addressed regulatory exposure for this spend tier. Here are three questions."

## War story: living inside a single-agent envelope

The problem decomposes into specialist scopes such as risk, financial structure, regulatory impact, and implementation planning. Each target field has one configured owner group, while the policy and guideline evidence available to those groups can overlap. One candidate design was a sub-agent per scope, coordinated by an orchestrator.

Governance set a different boundary. The first true agentic AI platform approved for production at the bank had a single-agent envelope: one agent, one approved scope, no multi-agent orchestration in v1. That removed the sub-agent design from the v1 option set.

The v1 design uses concurrent scoped extraction without sub-agents. The graph selects groups, dispatches registered calls, validates their schemas, and merges results according to the target-field ownership map. Cross-call coordination is not assigned to an autonomous model process; each call receives a bounded extraction task.

The workflow still provides branching dialog, multi-step state, tool use, and concurrent specialized work. Its reviewed control surface remains one agent calling tools. That operational distinction is more useful here than claiming a universal definition of an agent.

The cost was design discipline. Every time we reached for a multi-agent pattern (persistent cross-agent memory, inter-agent negotiation, agent-on-agent reasoning) we had to ask whether that could be expressed as deterministic graph logic plus MCP tools, or whether it fundamentally required multi-agent primitives. Capabilities that required the latter stayed outside the approved production design.

**The lesson that generalizes:** an early agentic deployment in a regulated environment is not about maximum capability. It is about making the reviewed boundary explicit and preserving reusable contracts. PAR Assist v1 is single-agent: its group taxonomy, scoped calls, validation, coverage analysis, state model, and MCP tool surface remain inside that reviewed boundary.

## What transfers

The pattern (**governance-shaped orchestration + typed action boundary + field-group retrieval + concurrent scoped extraction + retained workflow state**) is a candidate for enterprise workflows that combine (a) multi-turn state, (b) structured-form target outputs, and (c) regulatory audit requirements. PAR drafting is one instance. Applying it elsewhere still requires domain-specific controls, evaluation, and evidence.

The implementation can change while those control questions remain useful: what context reaches the model, which actions have typed contracts, what state is retained, where collisions surface, and how each boundary is tested.
