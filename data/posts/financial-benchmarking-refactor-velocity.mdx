The Financial Peer Benchmarking Platform&rsquo;s v2 was a focused concurrent refactor of the production v1 system in 2025. It was not a separate greenfield system, and the essential design work did not begin on the first day of the sprint. The short implementation window was possible because v1 had already exposed the operating problem, an earlier prototype had tested the architecture, and later evaluation results made that shelved direction worth revisiting.

Prior evidence, bounded scope, and decomposable interfaces turned a short window into a credible delivery period.

## V1 created the knowledge the refactor needed

The CFO Group benchmarks financial KPIs against public Supplementary Financial Packages from major Canadian banks. The source documents are public, but the language is inconsistent. Similar metrics can have different names, and similar names can refer to different definitions.

I built v1 as a rules-based benchmarking system. It established the catalog, supported query shapes, and operating relationships that v2 would later reuse. It also earned the 2025 CFO One RBC Team Award.

As the catalog grew, the maintenance problem became clearer. New metrics and near-duplicates expanded the matching rules and the disambiguation logic around them. V1 remained useful, but it also showed exactly where natural-language interpretation could reduce friction and where the system could not afford to become less controlled.

That operating knowledge mattered more than a blank-sheet architecture exercise. By the time v2 was considered, the problem was no longer hypothetical: we knew where ambiguity appeared, which query shapes were supported, and what failure looked like to an analyst.

## The first design stayed shelved

I explored a natural-language path before the refactor. The decomposition was sound, but the early evaluated implementation did not meet the ambiguity criteria. Near-duplicate KPIs produced the two failures that mattered most: choosing too confidently or asking for clarification too often.

The responsible decision was to keep v1 in production and preserve the design work rather than force the model-assisted path into service.

That pause was not wasted effort. It left behind a tested question: could a later implementation support an accept-or-clarify policy on the real catalog without making the score look like a guarantee of correctness?

When later evaluation results justified revisiting that question, the architecture did not have to be rediscovered. It still required implementation, integration, and testing, but the core trade-off was already understood.

## Decomposition made the window believable

V2 separated the query path into five responsibilities: intent parsing, semantic candidate retrieval, ambiguity handling, reviewed query construction, and result formatting.

Each stage could be built and tested without asking one model call to solve the entire problem. The catalog could be evaluated independently of SQL construction. The clarification policy could be evaluated independently of formatting. Reviewed templates and parameter binding could constrain executable queries without waiting for the language behavior to become perfect.

That decomposition reduced coordination inside the codebase. It also reduced scope. The refactor did not attempt to become a universal financial question-answering system, support free-form numerical reasoning, or redesign every user surface. It addressed one bounded path: turn an analyst&rsquo;s supported question into a resolved KPI, a reviewed query shape, and a result that could either proceed or return for clarification.

The two-week window covers the focused v2 module refactor against a production-proven foundation. It does not include the time spent building v1, learning the catalog, evaluating the earlier design, or productionising the integrated product.

## Contribution and integration

I led and implemented the focused refactor against the production-proven v1 boundary. Clear interfaces and deliberately narrow scope made the implementation window possible.

After the module was built, my direct report worked with the broader production team to incorporate it into v2. V1 continued serving as the production path during the concurrent refactor. The implementation was concentrated; integration and production delivery remained collaborative.

## What the sequence established

The refactor added a bounded natural-language path without discarding the controls v1 had earned. Ambiguous KPI requests could return to clarification. Executable SQL stayed inside reviewed templates with parameter binding. Retrieval scores informed routing but were not presented as probabilities of correctness.

The two-week window covered implementation; adoption, accuracy, and control completeness require separate evidence.

**A shelved design can preserve useful evidence.** Stopping the first attempt prevented an immature model path from becoming a production obligation. The prototype remained valuable because it captured decisions and failure cases that could be revisited.

**Velocity is downstream of prior operation.** V1 supplied a real catalog, real supported query shapes, and known failure modes. The sprint began with those constraints already visible.

**Decomposition creates options.** Separate contracts made it possible to improve one stage, reject an uncertain case, or integrate the refactor without replacing the whole product at once.

The result was not a two-week invention. It was a two-week execution window created by earlier restraint, accumulated operating knowledge, and a design narrow enough to finish.
