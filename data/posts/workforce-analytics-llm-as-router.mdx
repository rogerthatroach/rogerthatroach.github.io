The AI/LLM Workforce Analytics Platform began with a tempting shortcut: the fastest route to an impressive demo was also the wrong production boundary.

A broad-access agent could have accepted a financial question, called data tools, and worked toward an answer. That shape was easy to explain. It was much harder to explain who owned entitlement, which records could reach the model, and whether the calculation would remain stable for the same authorized inputs.

The platform took a narrower route. Model-assisted stages handle language interpretation and answer shaping. Deterministic code owns entitlement resolution and financial calculation. The design is less theatrical than a general agent, but it gives each part of the system a responsibility that can be reviewed.

## The shortcut we did not take

The problem began with cross-domain questions that moved through email and spreadsheets. A finance leader might ask for headcount by division, crossed with open positions and compensation cost. Analysts could assemble the answer, but a new slice or follow-up often restarted part of the work.

The data model made a generic assistant especially risky. Roughly 40,000 cost centres sit at the leaves of business-segment and geographic hierarchies. A request has to resolve to the caller&rsquo;s authorized subset before calculation. The model also has to distinguish questions about compensation cost, headcount, and open positions without becoming the authority for either permission or arithmetic.

The obvious prototype was one model with broad data tools. It offered a short path to a conversational demo, but it combined four different responsibilities:

- interpreting the question;
- resolving what the caller may access;
- calculating the requested result; and
- explaining that result.

That concentration was the problem. A strong language model did not make permission logic more reliable, and a fluent answer did not establish that the underlying calculation was correct.

## The boundary the problem demanded

I separated language work from controlled execution.

Model-assisted stages classify the request, extract scoped intent, and shape the response. A deterministic Python path resolves entitlement, retrieves the authorized data, and performs the calculation. On the declared path, the interfaces are designed to pass structured inputs and aggregates across those application boundaries.

The router handled intent and response shaping; governed code remained responsible for entitlement and calculation. The model had no declared authority to broaden the caller&rsquo;s scope or replace the governed computation.

That boundary also made failure more legible. A request can be rejected as out of scope. Entitlement resolution can fail closed. A calculation can return a structured error. Answer shaping can be checked against the aggregates it received. None of those controls proves the whole system safe, but each gives the production team a specific condition to test and monitor.

## Building the part the demo hides

The visible conversational layer was not the difficult part. The load-bearing work was translating the existing entitlement model into an executable scope and making the calculation path responsive enough for interactive use.

I built the permission-to-query translation and the employee-movement calculations that sit behind the model-facing stages. Cython was used in the compute-intensive path while the surrounding orchestration stayed in Python. Typed handoffs made the boundary between intent, authorized computation, and response shaping explicit.

The implementation deliberately encoded what was specific to the operating problem: supported domains, hierarchy resolution, entitlement checks, and calculation rules. A more generic agent abstraction would have weakened that control.

The production work also extended beyond the core algorithm. Interfaces had to agree on schemas. Failure states had to be observable. Entitlement and data changes had to be handled as operating conditions rather than one-time setup. Reviewers needed enough retained evidence to investigate a request without treating logs as proof of completeness.

## Building it and bringing it to production

From March through the November 2025 launch, I conceived, architected, and built the AI/LLM workforce analytics platform while leading its cross-functional productionisation. The same period included mentoring the 2025 Amplify cohort and a focused two-week refactor of the Financial Peer Benchmarking Platform. I remained hands-on across the application and model boundaries while front-end, data, infrastructure, and governance partners owned the surrounding delivery surfaces and controls.

The architecture helped the collaboration. Because responsibilities were explicit, each group could review a concrete boundary rather than debate a general promise about what the model would or would not do. The same separation shaped testing: language behavior, entitlement resolution, calculation, and response assembly could fail independently and therefore needed independent evidence.

## What changed

The workforce analytics platform entered production in November 2025. It supports approved questions across compensation cost, headcount, and open positions through dashboard, conversational, and report-oriented experiences.

The practical change was not that every finance question became automatic. It was that supported cross-domain questions gained an interactive path with entitlement applied before calculation. Users could ask a follow-up without restarting a multi-day email chain, while analysts and operators retained responsibility for the source data, supported query shapes, and interpretation of the result.

The architecture still carries operating dependencies. Entitlement catalogs have to be current. Every integration path has to preserve the declared boundary. Structured aggregates can still be sensitive. Generated phrasing can still be wrong. Tests, monitoring, access controls, and review are what keep the design honest in operation.

## What carries forward

Many enterprise systems do not need an LLM router.

Language interpretation benefited from model flexibility. Permission and arithmetic did not. Drawing that line early prevented the prototype&rsquo;s most impressive feature from becoming the production system&rsquo;s weakest control.

Each component should own the narrowest responsibility it can perform well. The handoffs should be observable, and the controlled path should carry the facts the model is only allowed to explain.
